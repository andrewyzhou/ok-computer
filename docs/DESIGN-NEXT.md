# OK Computer: Design for Phases 2–5

This document extends [DESIGN.md](DESIGN.md). Phase 1 is built and running. Everything here adds to it; nothing here replaces a Phase 1 rule unless it says so. The conventions in DESIGN.md section 21 apply to all new code.

Research for this document was done on 2026-10-13. Versions and prices are from that date; check them again before you pin a dependency.

## 0. Goals

1. Connect Computer to everything the owner uses: all Gmail accounts, Google Calendar, Slack DMs in every workspace, web search, a browser for sites without an API, and the owner's Claude history (on hold, section 10).
2. Keep **full observability**. For every new capability, record exactly what the agent saw, what it decided, which policy allowed it, and what happened. Nothing that reaches the model or leaves the machine is unrecorded.
3. Give the agent more power safely: a permission system with a reviewer model, taint tracking for untrusted content, a real sandbox for code, and sub-agents with fixed limits.
4. Make Telegram pleasant: formatted replies, streaming, reactions, and clear approval cards.

## 1. New principles

These add to DESIGN.md section 2.

1. **The trace is complete.** Each model call stores the exact request (system, messages, and the tool list it offered) and the exact response. Each tool call stores the raw result, the text the model received after wrapping and truncation, the policy decision, and any approval. Each MCP server, browser step, and sandbox command stores its own detail. Large payloads go to the blob store (section 2.1), never get dropped.
2. **The tool list is stable within a session.** Changing the tool list changes the prompt prefix, which breaks prompt caching and invalidates thinking blocks. Integrations are reached through a fixed set of discovery tools (section 3.4), so new servers and tools never change the `tools` parameter in the middle of a session.
3. **Risk comes from our config, not from the server.** MCP tool annotations such as `readOnlyHint` are hints. The policy engine (section 5) decides.
4. **Outside text is tainted.** When a run reads untrusted content (email, Slack, web, calendar invites from others, Claude history), the run is tainted. Tainted runs cannot take outbound actions without the owner's approval.
5. **Least privilege everywhere.** Minimal OAuth scopes, per-session tool profiles, sandboxed code, a dedicated browser profile.
6. **Prefer maintained existing servers, but own the sensitive paths.** Use official or well-maintained MCP servers where they fit. Write our own integration where the data is most sensitive or no server fits (Gmail across 8 accounts, unsubscribe).

## 2. Observability v2 (cross-cutting, built first)

### 2.1 Blob store

- Content-addressed files under `data/blobs/ab/cd/<sha256>` with a `blobs` table: `hash, size, mime, createdAt`.
- Every payload over 8 KB (tool outputs, MCP messages, page snapshots, screenshots, sandbox output, rendered requests) is stored as a blob. Rows hold the hash plus a short preview.
- Redaction runs before hashing, so a secret never reaches a blob.
- Blobs are never deleted automatically. The dashboard shows total size. A later `okc prune` command can remove blobs older than a chosen age that no row references.

### 2.2 New and extended tables

- `tool_catalog_snapshots`: `hash, tools (json), createdAt`. The exact tool list offered to the model. `model_calls` gets a `toolCatalogHash` column, so every call shows which tools existed.
- `tool_calls` gains:
  - `source`: `builtin`, `mcp`, `google`, `browser`, `sandbox`, or `subagent`;
  - `serverId` and `account`;
  - `riskLevel`;
  - `policyDecisionId`;
  - `tainted`: whether the run was tainted at call time;
  - `rawResultBlob`: the result before wrapping and truncation, when it differs from the exact model view in `output` (2.5);
  - `truncated`, `resultHandle`, and `outcome` (2.5).
- `policy_decisions`: `id, toolCallId, decision (allow | review | approve | deny), rule, reviewerModelCallId, reviewerVerdict, reviewerReason, approvalId, createdAt`.
- `mcp_messages`: every JSON-RPC message per server: `serverId, direction (out | in), method, rpcId, payloadBlob, latencyMs, createdAt`. This includes `tools/list` results and notifications. The run id is set when the message belongs to a tool call.
- The tables below are the plan for later milestones. Each one is created by the migration of the milestone that writes it (2.5).
- `browser_steps`: `taskId, runId, toolCallId, action, target, urlBefore, urlAfter, snapshotBlob, screenshotBlob, consoleErrors, blockedRequests, createdAt`. Plus one Playwright trace zip per browser task.
- `sandbox_execs` (on hold with the sandbox, 5.4): `runId, toolCallId, command, cwd, network (none | allowlist), exitCode, stdoutBlob, stderrBlob, filesChanged, durationMs`. Phase 5 M9 built it in migration 020 with more columns, and `sandbox_files` in place of `filesChanged` (5.8).
- `integration_events`: polled changes (new mail, calendar changes, Slack DMs) with `source, account, externalId, kind, summary, payloadBlob, seenAt`.
- `subagent_runs`: `parentRunId, childRunId, profile, task, resultSummary`.

### 2.3 Dashboard additions

- **Run timeline, nested.** A model call leads to its tool calls. Each tool call opens to show:
  - the policy decision and reviewer verdict;
  - the approval;
  - the execution detail: MCP messages, browser steps with a screenshot filmstrip, or sandbox output;
  - child sub-agent runs.
- **"What the model saw" per tool result.** Show the raw result next to the exact wrapped and truncated text that the model received.
- **Integrations page.** Each server and account with:
  - status and last error;
  - tool list and the catalog snapshot history;
  - auth state and token expiry;
  - polling status;
  - buttons to connect, reconnect, and pause.
- **Browser page.** Tasks with replay (screenshots and snapshots per step) and a download link for the Playwright trace.
- **Policy page.** Recent decisions, holds, denials, and the rules file.
- **Signals page.** Integration events and what the heartbeat did with them.

### 2.4 Acceptance

For any run, the dashboard can reconstruct, byte for byte, every input the model received and every action the system took, including actions inside MCP servers (as far as the protocol shows them), the browser, and the sandbox.

### 2.5 Decisions from phase 2 M1

- **Blob store.** `src/observability/blobs.ts` stores text only. `put` redacts and hashes the text. It writes the file to a temporary name and renames it, so a crash never leaves a short file under the hash, and it writes the file again when it is missing or damaged. The row is one `INSERT ... ON CONFLICT (hash) DO NOTHING`, so several processes can put the same text at the same time. There is no `refCount` (it counted puts, not references, and nothing read it); a later prune finds the blobs that no row names. A read checks the hash of the bytes and throws when it does not match, so a damaged file is an explicit error and never wrong text. There is no fsync: a hash check on read already turns a torn file into an error, and fsync costs 3 to 4 ms per put. A hash must match `^[0-9a-f]{64}$` before a read, so a URL cannot reach a path outside the store. Binary blobs (screenshots) come with the milestone that needs them.
- **The row keeps the model view.** `tool_calls.output` is the single exact model view, as JSON. It is always short (a long result becomes a preview), so it needs no blob. `rawResultBlob` holds the text the tool gave only when the model got other text: a preview, or a wrapped untrusted text. The read rule is **raw result = `rawResultBlob ?? output.content`**, except that a preview, a wrapped text, or a late result without a blob lost its raw text in a failed blob write (see 2.8). Both texts go through the same redaction. Migration 006 drops `modelViewBlob`, which was a byte-for-byte copy of `output`. In the seeded test database this makes 1 blob file instead of 6. The 8 KB rule of 2.1 applies to the later payloads (MCP messages, snapshots). Every call gets a row, also an unknown tool, invalid input, a denied call, and a call that waits for approval.
- **Model calls.** `model_calls.request` keeps the full request, tool list included. The tool list also goes to `tool_catalog_snapshots` (hash of the JSON of the `ToolSpec` list), and `toolCatalogHash` links the call to it. Rendered requests do not move to blobs yet.
- **Tables for later milestones.** A table comes with the milestone that writes it. Migration 004 created the other tables of 2.2 early, and M2 had to rebuild `mcp_messages` (migration 005). Migration 006 drops `browser_steps`, `sandbox_execs`, `integration_events`, and `subagent_runs`, which no code writes, and `tool_calls.costUsd`, because no tool costs money now (search runs through Chrome). `mcp_messages` has a `toolCallId`. `policy_decisions` also has `runId`, `toolName`, and `reason` (the text the agent gets). `tool_calls` also has `untrustedSource`.
- **One tool caller.** `src/tools/caller.ts` is the only path that runs a tool for the model: resolve, policy, review or approval, execute, model view, record. The registry no longer has an approval gate, and it has no method that runs a tool without the policy (the old `registry.run` skipped deny rules); unit tests use `runTool` from `test/run-tool.ts`. An approved call runs through `callApproved`, gets the `policyDecisionId` of the original decision, and is recorded on the original run.
- **Caller contract.** The provider refuses a `tool_use` without a `tool_result`, so one throw in the caller used to break every later request of the session until `/new`. `call` now never throws, and it follows one rule: **fail closed before the tool acts, fail open after it.**
  1. Before the tool acts: resolve, validate, compute the taint, decide, and write the decision row. If one of these throws, the tool does not run, the model gets "X did not run, because its policy check failed", and the log gets the error with `runId` and `toolCallId`.
  2. The decision row is written before the reviewer or the owner is asked, and their answers update it (`approvalId`, the verdict). So an approval never exists without its decision. If the approval request throws, the model is told that the call did not run, no approval row exists, and the decision's `reason` says why.
  3. A reviewer that throws sends the call to the owner; the turn goes on.
  4. The tool runs under the run's abort signal. If the run stops (timeout or shutdown) while a tool still runs, the call is **abandoned**: the model gets "did not finish … its effect is unknown, check before you try it again", and the row gets `outcome = 'abandoned'`. A stuck tool therefore cannot hold the session queue. If the tool finishes later, the same row gets `outcome = 'late'`, the raw result, a handle, and the source; the model view stays what the model saw. A `system_event` with the late result (and its taint, when untrusted) goes to the session through the queue, so the model does not repeat an action that worked. There are no per-tool timeouts. An approved call has no run, so it runs under the shutdown signal and the background run timeout, and is abandoned in the same way (see 2.6).
  5. After the tool acts: if the blob or row write throws, the error goes to the log with `runId` and `toolCallId`, and the model still gets the output. A gap in the trace is better than a second action. A failed blob write loses only the raw text; the row is still written (see 2.7).
  6. A tool that throws has its stack logged with `runId` and `toolCallId` (`ToolContext.toolCallId`); the model gets only the message.
  7. An approved call runs at most once: `callApproved` claims it with `UPDATE approvals SET startedAt = ? WHERE id = ? AND startedAt IS NULL AND status = 'approved'`, so an expired approval never runs. It does not claim when the signal already stopped, and it returns `started`, so the session note says "did not run" for a call that never started, and an expired claim says "expired", not "already ran". `resolveApproval` is a compare-and-set on `status = 'pending'` too, so a button and the dashboard cannot both win.
- **Session repair.** Each run starts with `repairSession` (`src/agent/recovery.ts`), inside the session queue. It gives each call of the last assistant turn that has no `tool_result` event a result, chosen from the trace: the recorded model view (with its `untrustedSource`) when the row exists; "the app stopped while X ran, it is unknown whether it finished" and a row with `outcome = 'interrupted'` when the decision let the tool start (`allow`, or `review` with a reviewer `allow`) but no row exists; otherwise "X did not run" (or "waits for approval #N"). The decision row is written just before the tool runs, so it serves as the intent record and no journal table is needed. When a user message holds both, tool results render before text: the provider requires this ("tool_result blocks must come FIRST in the content array", verified in the tool-use docs), and only a repaired result can follow a `system_event`. In a log without a repair no result follows text, so no earlier request changes.
- **Stale work.** A sweep runs at the start and on each scheduler tick. It closes only work older than the longest run timeout plus 5 minutes, because a run always ends at its timeout (a stuck tool is abandoned then): such runs become `aborted`; an approved call that never started becomes `expired`, does not run, and the session and the owner get "approved, but the app stopped before it ran, … ask again"; an approved call that started and has no row gets an `interrupted` row and the same two notes. The age test, not "everything from before this start", decides, because `npm run chat` can share the database with the live service, and its start must not close the service's live runs or expire its queued approvals. The sweep also skips the work that its own process holds in memory (the runs in `activeRuns` and the approvals in `flow.active`), whatever its age (see 2.6). The next run of each session repairs it; the sweep repairs only a session that belongs to one stale run (see 2.8). A pending approval that expires after 24 hours also sends a `system_event` to its session. Approved calls never run at start: an approval can be days old.
- **Outcome.** `tool_calls.outcome` stores only the three facts that a later read cannot find: `abandoned`, `late`, `interrupted` (null otherwise). Every other word is derived on read by the pure `outcomeOf` (`src/dashboard/outcome.ts`) from the row, its decision and its approval: `ran`, `failed`, `invalid`, `denied`, `held`, `waiting`, `approved`, `declined`, `expired`. A stored word for every state would need three writers (the caller, the approval flow and the expiry sweep) to stay in step. The run detail shows the word as a chip on each tool call, so a call that waits for the owner no longer looks like a success, and the policy view shows the decision's taint snapshot with a link to the run that read each source. `isError` is unchanged, because it controls what the model sees. `approved` is on the call that asked; the run after the approval is its own row, with its own word.
- **Two processes on one database.** There is no instance lease. Blob upserts and the compare-and-set claims (approvals, the automation claim, and the interrupted row of the sweep, see 2.8) keep the shared writes safe, and the sweep's age test protects live runs. One hazard stays: if both processes run the same session at the same moment, a run start in one can repair a call of a live turn in the other. Do not chat in the main session from `npm run chat` while the service answers there.
- **Known gaps after M1.**
  - A late result reaches the model only at the next run of its session, as a `system_event`, not in the turn that abandoned it.
  - A crash between an approved call's row and its `system_event` leaves the session without that result. The row exists, so the dashboard shows it.
  - Taint does not follow text through memory (since M4 this also opens a path past "always allow", see 7.1): a tainted session can write a daily note, and consolidation can lift it into `MEMORY.md`. Track this for Phase 2 M3, when untrusted mail arrives. Goal titles are the same kind of path: `goals_set` in a tainted session writes text that the volatile context of every later run shows. Automations and the heartbeat checklist carry their taint (see 2.6 and 2.7). The heartbeat prompt's "recent notifications" lines repeat old notification text without taint; the heartbeat has no external tools, so the impact is low.
  - `model_calls.request` stores each normalized request inline, so storage grows with the square of a session's length (about 14 MB for a simulated 60-turn session). A manifest of message hashes in the blob store would cut this by about 12 times; it belongs with the `okc prune` work.
  - The repair at run start reads the whole session once per run. The strategy already does this on every model call, so it is not the bottleneck.
- **Policy order.** A deny rule always wins. A tool with `needsApproval` always asks the owner. In a tainted session an `external` call always asks the owner, also when a rule allows it. Otherwise the last matching allow rule wins, and without a rule the risk level decides. The taint rule for `write` is the default review of `write`; an allow rule for a `write` tool also holds in a tainted session, so give such a rule only to tools that keep data on the PC.
- **Rules.** Code has built-in allow rules for the Phase 1 tools that change only local data (goals, automations, memory, heartbeat, consolidation, `message_owner`). `okc.policy.json` (optional, next to `okc.config.json`) adds rules after them: `{ "rules": [{ "tool", "session"?, "args"?, "effect": "allow" | "deny", "note"? }] }`. Patterns use `*` and ignore case; an `args` key matches a top-level input field, and an object value matches against its JSON text. An `allow` pattern must match the whole value, and when the value is a list it must match every item, so one good recipient cannot carry a bad one. This holds only for a list: on one free-text string a `*` also matches a comma or a `..` segment, so an allow pattern there checks only the start and the end, and a recipient or path field must be a list in the tool schema (see 2.9). A `deny` pattern matches anywhere in the value's text (the JSON text for a list or an object), so `*@evil.example` also stops `Eve <eve@evil.example>` and `eve@evil.example, a@home.example` (see 2.7). The matcher is linear (it goes back only to the last `*`), because a regular expression with several stars took 18 s on an 800-character argument that the model controls; it folds case like a regular expression with the `i` flag, so a non-ASCII character such as the Kelvin sign never matches an ASCII letter. A rule with an unknown key (for example `arg`) is invalid. An invalid file stops the process at start. The rule id is `builtin:<tool>` or `okc.policy.json#<n>`.
- **Reviewer.** `Reviewer` is a type; the engine takes it as an optional dependency. Until Phase 3 M3 there is none, so a `review` decision becomes an owner approval, and the decision row says so in `reason`.
- **Taint scope.** Taint covers the session since its last `session_reset`, not only the run, because the model still sees untrusted text in later runs of the same session. A tool marks its output as untrusted with `ToolOutput.untrustedSource`; the caller then wraps it with `wrapUntrusted`, and the `tool_result` event carries `untrustedSource`. Calls in the same model turn are decided before any of them runs, which is correct: the model wrote them before it saw any result.
- **Taint comes from the event log.** `sessionTaint` reads the session's events after the last `session_reset`, ordered by `seq`, never by time: the old query compared `tool_calls.createdAt` with the reset time, so a clock that moved back after `/new` made a tainted session look clean. The taint is what the model saw: `tool_result` events with `untrustedSource`, and `system_event`s with `taint`. A `system_event` that relays text from another session carries the taint of that session: an isolated automation's message to main, a heartbeat notification, the result of an approved call, and a late result (see the caller contract). Without this, untrusted text reached main untainted. Two partial indexes (`events_reset`, `events_taint`) keep the check at 0.03 ms for a 50,000-event session (31 ms without them); it runs before every tool call.
- **Taint provenance.** Each taint source is `{ source, toolName, runId, toolCallId, at }`: the first call that brought that source into the session, or into the session it was relayed from. `policy_decisions.taint` keeps a snapshot of it, so the reason for a decision survives `/new`. The approval message gives the policy reason and names each source with its tool, time, and run, because the taint often comes from an older run that the owner has forgotten.
- **Handles.** A raw result over 4,000 characters becomes its first and last 1,500 characters (never cutting a surrogate pair), wrapped when untrusted, then a note outside the wrapper with a handle `res_` plus 12 hex characters. `result_read { handle, query?, from?, length? }` pages by character offset or finds passages around each query word, at most 3,500 characters with the header, and the query has at most 200 characters, so its own output never needs a handle, also inside the longest wrapper; no cut splits a surrogate pair (see 2.8); it wraps text again when the source was untrusted, so reading it taints the session too. `result_read` is in the main and automation tool lists, not in heartbeat or consolidation sessions. A result that compaction clears keeps its handle, and summary validation counts handles as identifiers.
- **Dashboard.** The run timeline nests each tool call inside the model call that asked for it. A tool call shows its decision, rule, risk, taint, and handle, and it opens to the raw result (from the blob) next to the exact model view, and to the policy decision with the reviewer verdict and approval. A model call shows the tool count and opens to its catalog snapshot. New routes: `/api/blobs/:hash` and `/api/tool-catalogs/:hash`. The overview shows the blob store size.

### 2.6 Decisions from phase 2 M1, verification round 1

Three reviews (acceptance, failure injection, security) gave 18 findings: 14 distinct issues, because four were found twice. All were real, and each is fixed with a permanent test.

- **A deny rule wins in any order.** `decide` took the last matching rule, so a later allow rule cancelled an earlier deny rule, against the policy order above. Now any matching deny rule wins, then the last matching allow rule. The other option, "last match wins" with deny-then-allow exceptions, was rejected: a broad allow rule that the owner adds later must never open a recipient that a deny rule closed. A narrow allow rule without a broad deny gives the same exceptions, because the risk level is the default.
- **The sweep never closes the work of its own process.** The age test alone failed in the live process in three ways: an approved call that waited in its queue behind runs longer than the age limit was expired and then told "already ran"; a slow approved call was called interrupted while it ran, and its real row came second; and a forward clock jump (sleep, an NTP fix) aborted live runs. The options were an instance id with a heartbeat on each run and approval (a migration, a timer, and a lease), or the work that the process holds in memory. The memory sets were chosen: they are exact for the live process, which is the only process that the failures came from, and the age test still guards the work of a second process.
- **An approved call has a timeout.** It runs under `AbortSignal.any([shutdown, AbortSignal.timeout(backgroundTimeoutMs)])`, so a stuck approved tool is abandoned like a run tool and no longer holds its session queue. The timer starts when the call leaves the queue, not at the owner's click.
- **The decision links to its approval at creation.** `createApproval` writes the approval and `policy_decisions.approvalId` in one transaction, before the message to the owner. A crash during a slow message then leaves a decision that the repair reads as "waits for approval #N". `RequestApproval` now gets the decision id in `why` and returns only the output.
- **The owner sees every field.** The approval summary shows each top-level field on its own line. A value over 300 characters keeps its first 200 and last 100 characters with a mark that names the cut and points to the dashboard, so a short field after a long one (a channel, a recipient) is always visible. Values are redacted before the cut. The approvals page shows the full redacted input. Splitting the full input over several Telegram messages was rejected: the owner reads the card on a phone, and the fields that decide (recipients, channels) are short.
- **Taint follows text into automations and the heartbeat checklist.** An automation keeps the taint of the session that wrote its payload (`automations.taint`, migration 007), and a new payload replaces it. The first event of each run carries it, also for a main session after `/new`. The heartbeat checklist keeps its taint in a setting; the owner's checklist from the dashboard has none. The other option, no built-in allow for these tools in a tainted session, was rejected: it asks the owner for every routine that the agent sets up after it reads mail, and it does not cover a payload that was written before the taint.
- **Untrusted errors stay untrusted.** `Tool.untrustedOutput` names the source of every output of a tool, an error too, because an HTTP body or an MCP error can carry outside text. M2 integrations with `untrustedOutput: true` set it.
- **Redaction.** `registerSecret` adds one escaped form for each JSON level, up to four, so a secret with a quote stays hidden in json inside json. The caller redacts a result before the preview cuts it, so a secret on the cut is never stored in part.
- **Smaller fixes.** A thrown `null` or string no longer breaks `call` (`errorText`), and the late path of an abandoned tool logs its errors instead of an unhandled rejection. A tool call in a reply cut at the token limit gets a row (`caller.notRun`), so the timeline shows it as `invalid`. `result_read` limits its query to 200 characters.
- **Known residual.** An approved call that ran, but whose trace write failed (fail open), has `startedAt` and no row. After the age limit the sweep reports it as interrupted, which is wrong only in that rare case; the session already has the real result.

### 2.7 Decisions from phase 2 M1, verification round 2

Three more reviews gave 18 findings: 14 distinct issues (the backslash secret was found three times, the result search cost and automation taint twice each). All were real, and each is fixed with a permanent test.

- **Redaction works on strings, not on JSON text.** A registered secret that starts or ends with a backslash or a quote is a part of its own escaped form, so a replacement in finished JSON text could take one half of an escape. The payload was then invalid, `appendEvent` committed it before it failed, and the append-only log blocked the session for good. `redactedJson` now redacts each string leaf (and each key) in a `JSON.stringify` replacer, so its output is always valid. The escaped forms of round 1 stay, because a string can hold JSON text, and `redact` replaces the longest form first, so that inner JSON text also stays valid. The MCP recorder, the logger, and the approvals page (`redactValue` after the parse) use the same path. Round 1 tried a replacer alone and rejected it because it misses JSON inside JSON; the two together cover both.
- **Automation text keeps its taint.** The name of an automation is text that its runs and the volatile context of every run read, but only a new payload changed the taint, and a new payload also cleared it. Now a session that writes the name or the payload adds its taint, and the old taint stays until both fields get new text. This replaces "a new payload replaces it" of 2.6. A pause or a new schedule writes no text and adds no taint, so a pause from a tainted session does not make each later run need approvals. `automations_list` marks its output untrusted (with the sources of the listed automations) when one of them is tainted, and the volatile context replaces the name of a tainted automation with a fixed phrase. The other option, a taint on the volatile context, was rejected: it would taint every session while any tainted automation is pending.
- **Relayed text is wrapped.** The message that an isolated automation or the heartbeat sent to the owner goes to main inside `wrapUntrusted` when the run was tainted, and the id stands for a tainted automation name. `wrapUntrusted` also neutralizes `</system_event>` and `</note>` (and, since 2.8, the tags of a summary request), so wrapped text cannot close the message that holds it. A render-time wrap of every tainted `system_event` was rejected: approved and late results already hold a wrapper, and a second wrapper would remove their closing tag.
- **The handle limit applies to the wrapped view.** The test was on the raw text, so an untrusted result just under 4,000 characters had a wrapped view over the limit and no handle, and the trim of an old turn cut its middle for good. The source in the wrapper has a limit of 120 characters (the taint keeps it in full).
- **`result_read` search is one pass.** It made one span for each match of each word over the whole result: 1.3 s and 650 MB for 26 one-letter words over 8 MB, on the event loop of the live app. Now one alternation regex walks the text in order, merges spans as they come, closes a span at the read limit, and after the passages are full only counts up to 10,000 more matches ("more than N passages"). Dropping short words was rejected: a two-letter id is a fair query, and the scan limit already bounds the work.
- **A blob failure keeps the row.** `blobs.put` was a part of the row insert, so one failed write (EPERM from a scanner, a full disk) dropped the decision link, the input and the model view. Now the blob has its own try; the row gets `rawResultBlob = NULL`. A late result gets `late` also when its blob fails.
- **The caller does not wait past the run.** The request to the owner and the reviewer race the run's signal, as the tool does. After a stop the model gets "did not run … if the request reached the owner, the decision comes back as a system event", and a late error goes to the log. `ReviewRequest` has a `signal` for the model call of Phase 3.
- **Content that is not text.** The registry turns content that is not a string (an adapter bug) into text, so the caller cannot throw after a tool acted.
- **Compaction boundary.** A repaired result comes after the events that arrived while the process was down, so a boundary on such an event kept the result without its call. `chooseBoundary` now keeps the ids of the results whose call it did not reach and takes a boundary only when that set is empty. A render-time guard that drops an orphan result was not added: the boundary is the only place that can split a pair.
- **Approvals.** Each value in the summary is JSON text (with U+0085, U+2028 and U+2029 escaped too), so a line break cannot forge a field or a "Why:" line. When `owner.send` returns false, the model is told that the owner was not reached and the approval is on the dashboard. `resolveApproval` no longer expires approvals; an approval past 24 hours cannot be resolved ("expired … did not run"), and the next sweep expires it with its session note.
- **Deny patterns match anywhere.** An anchored deny pattern let `Eve <eve@evil.example>`, a trailing dot or space, an address list in one string, and an object list past `*@evil.example`. A deny rule now matches its pattern anywhere in the value's text. Allow rules stay anchored and per item. A deny rule that matches too much stops a good call; one that matches too little lets a bad call out.

### 2.8 Decisions from phase 2 M1, verification round 3

Three more reviews gave 19 findings, all real, each fixed with a permanent test. None was skipped.

- **No cut splits a surrogate pair.** `src/text.ts` has `safeStart`, `safeEnd`, `headOf` and `tailOf`. `result_read` pages and search passages, the trim of old results, the approval summary, the source in the wrapper, and the other cuts of text for the model use them. A lone half stays in the append-only log, and a provider can refuse each later request with it. A page that starts inside a pair starts at the next whole character, and the "use from N" note gives the adjusted end.
- **The wrapper keeps the length of the text.** A closing tag inside untrusted text keeps its characters, and its `<` and `>` become `[` and `]` (`</note>` becomes `[/note]`). The old replacement, "[removed closing tag]", was three times longer than `</note>`, so tag-dense text grew past the preview limit, and a tag without its `>` took all the text after it. The other option, a shorter fixed word, still loses the tag name. With the length kept, a wrapped text over the limit is always over 3,000 characters, so head and tail never overlap.
- **The search budget counts its frame.** The passages of a `result_read` search share `READ_LIMIT` with the header (with the query) and the last line, so the output stays under the handle limit inside a wrapper with the longest source.
- **The raw result after a failed blob write.** A preview, a wrapped text and a late result always get a blob, so such a row without one lost its raw text. The run page says so, and an abandoned or interrupted call says that the tool gave no result. A new column was not needed: the rule is exact for the rows that the caller writes.
- **Two more compare-and-set claims.** The automation claim updates only when `nextRunAt` is still the value that the tick read, so the service and `npm run chat` never both run a due job. The interrupted row of the sweep is an `INSERT ... WHERE NOT EXISTS`, and only the sweep whose insert writes the row sends the notes. A status for interrupted approvals was rejected: it adds a state that `outcomeOf` and the approvals page must learn.
- **Repair of sessions without a next run.** The sweep repairs the session of a stale run when the key ends with the run id (`auto:<id>:<runId>`, `heartbeat:<runId>`); no other process can have a live turn there. `/new` repairs main before the reset, and a failed repair does not stop `/new`. The repair handles each call on its own: a call that fails gets the "unknown whether it finished" text and a log line. `redactedJson(undefined)` is now `"null"`, so a call without arguments keeps its row. A shared session such as `consolidate:<day>` is left to its next run.
- **Process safety.** The channel callback catches a rejected `router.handle`, and the router replies to the owner when an approval fails. A tool source that is not text stays untrusted (`true` becomes the tool's `untrustedOutput` or its name).
- **Approvals.** A typed `/approve N` replies with the stored card and its buttons; only a button or the dashboard approves, and `/deny N` still denies at once. The assistant can send a false card through `message_owner` with the id of a real approval, so a command that runs the stored input without showing it is a confused-deputy path. A fixed prefix on `message_owner` text was rejected: the owner reads a phone notification, and a prefix does not stop a false card. Each approval note (denied, approved, expired, stale, interrupted) carries the taint snapshot of its decision and wraps the summary, because the summary is text that the model wrote. The card marks a field that the redaction changed ("the tool gets the real value") and a word that mixes Latin letters with letters of another script, with the code points. A built-in deny for an input with a registered secret was rejected: the model sees only redacted text, so the case is rare, and the mark lets the owner decide.
- **Redaction.** The slot runner redacts a provider error once for the row, the result, and the reply to the owner; `runAgent` redacts the run error; the caller redacts `untrustedSource` with the content.
- **Deny rules read normalized forms.** A deny rule also tests the NFKC form after percent decoding (with `。` and `｡` as `.`) and the `href` of each value that parses as a URL. Allow rules keep the raw text and the ASCII fold.
- **Compaction.** The wrapper also neutralizes `</conversation>`, `</previous_summary>` and `</summary>`, and the summary prompt asks to keep text from an untrusted block as quoted data with its source. Dropping identifiers that occur only in untrusted results was rejected: a meeting time in an email is often the fact the owner needs.
- **Known gaps after round 3.** A late result or an approval result of a per-run session goes to that session, which no run reads; it is not relayed to main. Main got the relay with the abandoned text, so it can still repeat the action.

### 2.9 Decisions from phase 2 M1, verification round 4

Three more reviews gave 12 findings. 11 are fixed with a permanent test. One (an allow pattern on one free-text string) is documented and pinned by a test, and its fix waits for the first tool with a path or a recipient field.

- **Deny rules test each string.** The JSON text of a list or an object escapes `\` and `"`, so a deny pattern with either one never matched a list item or an object field (`C:\Users\owner\.ssh` in `{ from: ... }`, `rm -rf "/"` in an argv list). A deny rule now tests the JSON text and each string leaf at any depth. Each form also gets a copy without default-ignorable characters (soft hyphen, zero width space, word joiner, byte order mark), before NFKC, and the `href` of each `http(s)://` URL in the text, not only of a value that is a URL as a whole. A deny that matches too much only stops a call.
- **Allow patterns on free text.** A `*` also matches a comma, `<`, a space or a `..` segment. So `*@home.example` allows `"eve@evil.example, bob@home.example"`, and `C:\notes\*` allows `C:\notes\..\Users\...`. A heuristic that refuses separators in the starred part was rejected: it breaks an allow rule on any free-text field (`text: *`). A typed rule (`email` splits, `path` resolves) is the planned fix, with the first tool that has such a field. Until then a recipient or path field must be a list in the tool schema; a test pins the limit.
- **Redaction.** The tool list snapshot is `redactedJson(tools)`, the same text as `request.tools`, so the hash also covers the redacted text. The decision store redacts `reason` and `reviewerReason` in one place, and the caller redacts the error of a failed reviewer before it goes on the card.
- **An abandoned approved call.** `callApproved` returns `abandoned`. The owner and the session read "the tool started, but it did not finish in time, so its effect is unknown", not "the tool failed". A late result also goes to the owner, who approved the call; the session gets it as before.
- **The trace is a record, not a data path.** The heartbeat and the consolidation read the successful calls of their run from the event log (`succeededCalls`), which the run cannot go on without. A lost `tool_calls` row no longer drops a notification or makes a saved consolidation run again. `recentNotifications` still reads the trace; it only gives the prompt a hint against repeats.
- **Limits.** The run timeouts are at most 2^31-1 ms, because Node sets a longer timer to 1 ms. A schedule time must be before the year 10000 and an interval at most 366 days, because the store compares ISO text and `+010000-...` sorts first; `nextRun` gives no run past that limit.
- **Untrusted sources.** Only a missing source or `false` means trusted output. An empty or blank source becomes the tool's `untrustedOutput` or its name.
- **Tool call ids.** The OpenAI-compatible adapter gives a new id to a call whose id an earlier call of the request has, or that has none. The trace, the decisions and the repair find a call by run and id. Changing the repair to match by position was rejected: the id is the key everywhere, so the source is the right place.
- **The approval card.** Invisible and direction characters show as `\u` codes with a mark; a variation selector and a joiner after an emoji stay. The script check runs on each run of text between spaces and JSON marks, so an address split by an invisible character and a host made only of look-alikes (`https://аррӏе.example`) get a mark. Escaping every non-ASCII character was rejected again, because accented names and other languages become hard to read; a sentence without Latin letters stays plain.
- **Known gaps after round 4.** An allow pattern on one free-text string (above). An id collision after a compaction inside one run is still possible with a server that numbers its calls, because the earlier call is no longer in the request. A punycode form of a URL host is not shown on the card.

## 3. Integration layer

### 3.1 MCP client

- Use `@modelcontextprotocol/client` v2 (2.3.x), the stable TypeScript SDK line for MCP spec 2026-07-28. Do not use the v1 `@modelcontextprotocol/sdk`.
- Transports: `StdioClientTransport` for local servers (it uses cross-spawn, so `npx` works on Windows) and `StreamableHTTPClientTransport` for remote servers.
- One `McpConnection` per configured server. It handles:
  - start and stop;
  - health checks with `ping`;
  - restart with backoff;
  - stderr capture to the log;
  - a `listChanged` handler that marks the catalog as stale.
- Every request and response goes through one wrapper that writes `mcp_messages`.
- Support elicitation (deferred in M2, see 3.7): form mode becomes a Telegram or dashboard prompt, and url mode becomes a link to open. Do not implement sampling (deprecated in the 2026-07-28 spec).

### 3.2 Integration registry

`okc.integrations.json` (non-secret, committed with safe defaults) lists each integration:

```json
{
  "id": "slack-work",
  "kind": "mcp-http",
  "url": "https://mcp.slack.com/mcp",
  "auth": { "type": "oauth", "clientRef": "slack-work-app" },
  "tools": { "allow": ["search_messages", "read_conversation", "send_message"] },
  "risk": { "send_message": "external" },
  "untrustedOutput": true,
  "sessions": ["main", "auto", "sub:inbox"]
}
```

- `kind`: `mcp-stdio` (with a pinned `command` and `args`; never `@latest`), `mcp-http`, or `builtin` (our own in-process integrations such as Google).
- Tools not in `allow` are invisible. Every exposed tool gets a risk level from this file. Its default is `write` when the server says `readOnlyHint` and `external` otherwise.

### 3.3 Secrets and OAuth

- Store tokens and API keys in the system credential store (the Credential Manager on Windows, the login Keychain on macOS, the Secret Service on Linux, or the kernel keyring when no Secret Service runs) through `@napi-rs/keyring`. It ships prebuilt binaries and needs no build tools. The database stores only a reference.
- OAuth flows use a loopback callback server on `127.0.0.1:4318/oauth/callback`. Start a flow from the dashboard Integrations page. Validate `state` (the MCP SDK does not) and finish with `transport.finishAuth`.
- The owner completes OAuth on the PC itself, or over a remote desktop. A phone cannot reach the loopback callback.
- Expiry and revocation are visible. Warn the owner in Telegram when a refresh fails, with a link to reconnect.

### 3.4 Tool exposure: stable list plus discovery

The model sees three groups of tools:

1. **Core tools**, always present: the Phase 1 tools plus `result_read`, `delegate`, and the discovery pair below.
2. **Pinned integration tools**, chosen per session profile in config and namespaced as `<integration>__<tool>` (for example `google__gmail_search`). A short list of the tools the profile uses most. They are fixed for the life of a session.
3. **Discovery**, for everything else:
   - `tool_search { query, limit }` returns matching tools with name, description, and input schema, within a budget (1 KB per description; the whole answer stays under the handle limit of 3.5, see 3.7).
   - `tool_call { name, arguments }` validates the arguments against the stored schema, runs the tool through the policy engine, and returns its result.

The `tools` parameter therefore never changes inside a session. A changed server catalog takes effect at the next session or the next run start, and is recorded as a new catalog snapshot.

**Schema normalization.** Translate each schema to what the provider accepts:
- Anthropic takes JSON Schema almost unchanged.
- The OpenAI-compatible adapter dereferences `$ref` and simplifies `oneOf` and `anyOf` for local models.
- Tool names must match `^[a-zA-Z0-9_-]{1,64}$`. Keep a map from each name back to its server and tool.

### 3.5 Large results and handles

- When a result is over 4,000 characters, the model gets a preview (head and tail) and a handle such as `res_7f3a`.
- `result_read { handle, query? , from?, length? }` searches or pages through the stored result.
- Results that compaction cleared keep their handles, so the agent can look up old detail without stale content in context.

### 3.6 Polling and signals

- Integrations poll on schedules (Gmail and Calendar every 15 minutes, Slack DMs every 15 minutes) as system automations. Polling is code, not a model call.
- New items become `integration_events`. A cheap classification pass on the `utility` slot labels each one: `needs_reply`, `deadline`, `event_change`, `newsletter`, `noise`.
- The heartbeat gets a bounded digest of unhandled signals (at most 20, newest first) instead of raw tool access. It decides whether to tell the owner and marks signals handled.
- Detectors written in code, each with tests:
  - "an email mentions a date and it is not on the calendar";
  - "a calendar event starts in under 2 hours";
  - "a DM has been unread for over 4 hours".

### 3.7 Decisions from phase 2 M2

- **Discovery only.** M2 builds group 3 of 3.4 (`tool_search` and `tool_call`) and no pinned integration tools. The two tools have fixed text, so the `tools` parameter is byte-stable by construction, also across a `list_changed`, a crash and a reconnect. The allowed names of a session come from `okc.integrations.json`, never from a catalog. Without the file, no discovery tool is registered, so the prompt prefix of an app without integrations does not change. Pinned tools come with the milestone that needs them (M3), with a frozen spec per session.
- **Live catalog.** There is no catalog freeze per session or run. A new tool list shows in the next search, and a schema change between a search and a call gives an "invalid input" that names the new fields. Each changed list is a version in `tool_catalog_snapshots` + `integration_catalogs`. The last version of each server is loaded at start under the current allow list and risk map, so `tool_search` works before the server answers. An equal list reuses the compiled catalog. The names of hidden tools are not part of a version.
- **The registry unwraps `tool_call`.** `registry.resolve` turns `tool_call {name, arguments}` into the integration tool it names, before the policy. The decision, the approval card, the trace row and the outcome all name the real tool (`notes__add_note`), so `okc.policy.json` rules work on real names. Only the `tool_result` event keeps the model's own call. A built-in tool, a nested `tool_call`, and a name outside the session's allowed names are refused. A failed check is recorded under the named tool, with `source = 'mcp'` and its integration; its message can quote the server's schema, so for an untrusted integration it carries the tool's untrusted source and taints the session. The lookup takes the session key and reads the current config, so an approved call whose session lost the integration does not run, and an approval whose tool is gone says so. The repair at run start names the inner tool.
- **Names.** `<id>__<tool>` when that is a valid name; otherwise the cleaned name plus 6 hex characters of the SHA-256 of the original name. A name depends only on the id and the server's name, so an approval made days earlier cannot bind to another tool. A collision inside one server is refused at intake.
- **Search budget under `HANDLE_OVER`.** This replaces the 16 KB of 3.4, which M1's 4,000-character handle rule would cut in the middle. The whole answer with its wrapper stays under `HANDLE_OVER - 600`. A tool whose schema does not fit gets one line and "search for the exact name"; an exact-name search returns one full schema, through a handle when long. Each hit names its integration and says what its risk means ("risk external: the owner approves each call"). A search without a hit lists the tool names (at most 1,500 characters).
- **Search output is untrusted** (`mcp catalog: <id>`), because a server writes its descriptions and can change them at any time. So is every output of an MCP tool, also our own "did not run" text. Cost: after a search, allow rules on `external` tools stop applying until `/new`. Accepted until the reviewer (Phase 3 M3).
- **ajv with a guard.** Server schemas are checked with the SDK's bundled ajv (`@modelcontextprotocol/client/validators/ajv`, no new dependency), not zod's `fromJSONSchema`, which refuses a valid `oneOf` with a const discriminator. ajv runs without `useDefaults` or `coerceTypes`, so the server gets the bytes the owner approved. Before the compile a guard refuses a schema that is not an object, is over 16 KB or over 32 levels, and removes `pattern`, `patternProperties` (and then `additionalProperties: false` and `unevaluatedProperties: false`), `$id`, `$anchor` and `$dynamicAnchor`: a server `pattern` took 11 s on 29 characters, and `$id` let one server replace another server's validator. The guard walks every value, not a list of keywords (draft-07 `dependencies` and a `$ref` to an unknown key such as `#/x-shared/slow` got past a list); only the names in `properties`, `$defs`, `definitions`, `dependentSchemas` and `dependencies` are kept, and data keywords (`const`, `enum`, `default`, `examples`, `required`) are copied. A `$ref` must point to a part that the walk loosened as a schema; a reference into data or into a map of names is refused with the reason. The guard only loosens; the server checks again. The client never checks `outputSchema` (see Connection), so no server pattern runs on the event loop. A dialect that the SDK's ajv does not know (for example draft-04) moves the tool to `rejected` with the reason. Round 2 adds a limit on the work of one check and removes `format: url` (see 3.8).
- **Connection.** The run owns cancellation, not the SDK: `tools/call` gets no run signal and no 60 s timeout (an abort makes the SDK drop the answer, so the M1 late result could never arrive). A 1 h cap ends a request that never answers as `unknown`; the SDK then sends `notifications/cancelled`, which the trace links to the call (a test pins it). That is the only cancel in M2. Outcomes are typed: `result | not_sent | refused | unknown`. `tools/call` goes out as a plain `request`, not `callTool`: `callTool` checks the result against the server's `outputSchema` (running server patterns on the event loop) and throws a protocol error for a tool that ran. `refused` means that the server's answer was a JSON-RPC error; when a result came but cannot be read, the outcome is `unknown` with `answered`, and the model hears that the tool ran. No ping goes out while a `tools/call` waits, so a server with one thread is not closed mid-call. The trace keeps at most 100 server notifications a minute (one row says where it stops; `list_changed` and `cancelled` have their own limit of 10 a minute each, see 3.8). A 401 or 403 from an HTTP server is `not_sent`, and for a bearer entry the state names the secret to update. The outbound trace write fails closed and the inbound one fails open. A stop or a second start cancels a stale attempt. Backoff is 1 s, 5 s, 30 s, 2 min, 10 min, reset only after 60 s of healthy uptime. Version negotiation is pinned to `legacy`, because `auto` starts a second, unrecorded stdio process. On Windows a close ends the descendants of a stdio server too. stderr is limited to 100 lines a minute and 2,000 characters a line. The transport error is kept, so a reason reads "Connection closed: spawn … ENOENT".
- **No wait for a connection.** A call while the server is not connected returns at once with why: not connected yet, not connected with the reason and the next try in the owner's time zone, paused, not signed in, or the chat process. A wait would hold the session queue, and the call did not leave, so a retry is safe.
- **`unsent` rows.** When the transport refuses a request after its out row was written, a second row with `direction = 'unsent'` and the error closes it. It is written only for an error that shows the message did not leave (`not_sent`): an HTTP `send` also reads the answer, so other send errors can follow the action, keep only the out row, and are `unknown`. No migration: `direction` has no check constraint.
- **Pagination.** The connection walks every `tools/list` page (capped at 64 pages, which throws instead of giving a partial list), also for the `list_changed` refresh. A test pins it. (Round 3 moved the walk from the SDK into the connection, see 3.9.)
- **Secrets.** `@napi-rs/keyring` loads only when the app uses it. A value over 1,200 UTF-16 units (one credential holds 1,280) is stored in parts under a new generation, then a head with the count and a hash, then the old parts are deleted, so a crash leaves the old or the new value. A delete removes the head first and the parts after it, and a head whose parts are gone reads as no value, so a damaged token set parks the integration instead of stopping it. The target of an entry is `<ref>.ok-computer`. A stdio entry run by `npx`, `pnpx`, `bunx`, `pnpm dlx`, `yarn dlx`, `npm exec`, `npm x` or `bun x`, also behind `cmd /c` and after an option such as `--yes`, must name an exact `x.y.z` version for each package it downloads; a tag, a range or no version is refused at load.
- **OAuth is parked until the owner clicks Connect.** An OAuth integration without tokens makes no request at start: no discovery, no registration, no flow. The provider never opens a browser. A flow is keyed by `state`, works once, for one integration, for 10 minutes. The callback on `127.0.0.1:4318` listens only while a flow waits, accepts only a loopback host and GET, and answers fixed text. A refresh is single-flight through the transport `fetch`, and only a successful refresh is shared. A refresh that fails because the sign-in server is down (no answer, a 5xx, `server_error`, `temporarily_unavailable`) makes the SDK ask for a new sign-in; the app then makes no link, a call says to try later, and a start retries with the backoff, so a short outage never becomes `needs_auth` or a message to the owner. Connect is single-flight per integration, the callback port starts once, its close timer follows the last link, and a sign-in finished after Pause leaves the integration stopped. The same wrapper logs each sign-in step (no query, no body) and writes a failed step's server text to `integration_state.lastError`. An SDK save that only adds the issuer to stored tokens does not count as a sign-in. `@hono/node-server` runs with `overrideGlobalObjects: false`, because its own `Response` class made the SDK misread `invalid_grant` in the live process.
- **One sign-in message.** The owner gets one Telegram message, with the server's text and the link to the page, only when a sign-in that worked (`authorizedAt` set) stops working in a call or a connect attempt that the owner did not start. A first sign-in, a crash loop and a restart after a revoke (the SDK deleted the tokens, so the integration is parked) send nothing.
- **Chat mode does not connect.** `npm run chat` keeps the same tools and stored catalogs, so its prefix is the same, but never starts a server; its calls say the integration runs only in the background app. This closes the refresh race between two processes, duplicate stdio servers and the port fight. Two service instances would still race; the supervisor runs one.
- **Schema normalization.** Anthropic gets the schema unchanged except `$schema`. The OpenAI-compatible adapter gets a plain schema: references in place, a union simplified only where a type list or an enum says it exactly, null variants dropped, and a union of objects kept as `anyOf` (the first-shape rule made `automations_create` accept only one schedule kind). A budget of 2,000 output nodes and 32 levels makes a part past the limit accept any value: looser, never stricter. The walk goes into every value, so a reference in `prefixItems`, `not` or `if` is put in place too. Integration schemas never enter `tools`; `tool_search` shows the guarded original.
- **Elicitation is deferred.** The client declares no elicitation capability. A form that asks for data is an outbound channel and needs its own approval design.
- **Dashboard.** `GET /api/integrations`, `GET /api/integrations/:id` (versions with diffs, recent calls with outcome words, JSON-RPC messages), `POST …/connect` (reconnect for every kind; resumes a paused integration), `POST …/pause {paused}` (survives a restart), `GET /api/mcp-messages/:id`. The pages reload on a log line of an integration. A changed description of an allowed tool is red in the version list. The run timeline shows the JSON-RPC messages of each integration call.
- **No migration.** Migrations 004 and 005 have every table and column M2 writes. `tool_calls.source = 'mcp'` and `serverId` are now written.
- **Known gaps after M2.**
  - Orphan stdio servers after a hard crash of the app (the tree kill runs only on close).
  - The SDK's 10 MB stdio line limit, and the same limit on an HTTP answer (3.10): a larger result closes the connection, and the call is `unknown`.
  - `list_changed` is asynchronous: a search right after a call that changes the list can see the old list.
  - No UI to store a pre-registered `clientRef` (Slack, Phase 3 M1); use `cmdkey`.
  - HTTP session-id expiry of a remote server is untested.
  - A stdio write before a spawn error lands in the pipe buffer, so the trace shows an out `initialize` that never reached a process. The status and last error say why.
  - Nothing prunes `mcp_messages`, blobs or catalog versions. A server that sends a new tool list each second still grows the database; an equal list costs one short row (3.8).

### 3.8 Decisions from phase 2 M2, verification round 2

- **The guard limits the work of one check.** The SDK gives ajv `allErrors`, so every branch of `allOf`, `anyOf` and `oneOf` runs. A 1.6 KB chain where each level refers twice to the next level ran out of heap memory (the process dies, no catch helps), and 31 levels of `allOf` took 7.9 s on a valid input. The guard now counts the parts of the schema with each `$ref` put in place and refuses the tool over 5,000 parts: a 16 KB schema without references has fewer, so a reference cannot make a check larger than the byte limit already allows. It also refuses a recursion that comes back to itself without a step into the input (it never ends), or on two paths where one is the start of the other, with wildcards for `additionalProperties` and `items` (`a = allOf [items a, items a]` doubles per level of input; the paths `x` and `x.x` split a chain in fib(n) ways). A filter with `and`/`or`, a JSON value and a binary tree stay. The prefix rule also refuses `x` with `x.y`, which is linear; it cannot tell the two apart, and such a schema is rare. Refusal and not loosening, because the guarded schema is also what the model reads, and the dashboard shows the reason. A worker thread with a time limit was not taken: the check runs inside a synchronous zod refinement, and a worker per check costs more than the count. `format: url` is removed, because ajv-formats checks it in quadratic time (40,000 characters took 1.2 s); every other format stayed under 3 ms on 20,000 characters, so they stay for the model.
- **A stored catalog goes through the guard of today** at the start, so a schema that an older guard kept cannot run before the server answers.
- **`list_changed` and `cancelled` have their own limit** of 10 a minute each in the trace, with the same row that says where it stops. 20,000 of them held the event loop for 25 s; now 0.4 s, the same as other notifications. A flood of other notifications still cannot hide them. A `tools/list` answer that the connection already recorded gets a short row with the SHA-256 of its result: an unchanged list of 200 tools was 100 KB a refresh. Both rate windows (the trace and stderr) start again when the clock moves back.
- **An inbound blob failure keeps the row** with a note in place of the payload, like M1's `tool_calls` rule. A message out still does not go without its whole trace.
- **An unreachable HTTP server is `not_sent`**: a fetch error whose cause is `ECONNREFUSED`, `ENOTFOUND` or `EAI_AGAIN` fails before a byte leaves. The connection closes, so the backoff starts at once. `ECONNRESET` stays `unknown`, because a reset can come after the server read the request (a call on an old keep-alive socket of a stopped server gives it too).
- **A tool output names its effect** (`effect: 'none' | 'unknown'`). An integration call that was not sent is `none`; a request with no answer is `unknown`. An approved call with no effect makes the approval `pending` again, so the owner can approve it when the integration can take it (paused, connecting, the chat process, a failed trace write); the words say that the tool did not run. The crash sweep ignores the row of such an earlier attempt (rows from before the start mark). An abandoned call that later ends without an answer stays `abandoned`, and the owner and the session read that its effect is still unknown, not that it finished.
- **A repaired row of an interrupted integration call** has `source = 'mcp'` and its integration, so the page shows the call whose effect is unknown.
- **A credential manager failure at the start** goes to the log, and the connection starts anyway: it reads the tokens again, and its retry shows the error and tries again. Before, the integration stayed stopped with no error.
- **The version check reads more runner forms**: `cmd /c` and `/k` (also one text with spaces), `npm x`, options before the runner word, and `-p=`. Not read: an option with a value before the runner word, such as `npm --prefix dir exec`.

### 3.9 Decisions from phase 2 M2, verification round 3

- **The tool list is read tool by tool.** The SDK checked a whole `tools/list` answer against its strict tool schema, so one tool with a sloppy shape (no `inputSchema`, `required: null`, a text `readOnlyHint`, a `null` description), also a hidden one, threw the list away, and the integration retried for ever. The connection now sends `tools/list` itself with a lenient result schema (`tools: unknown[]`, `nextCursor`), walks the pages (64 at most; a repeated cursor ends the walk), and refreshes after `list_changed` with its own 1 s debounce. The catalog checks each field: a tool without a name is skipped, a hidden tool stays hidden, and an allowed tool with a bad schema moves to `rejected` with the reason. A missing `inputSchema` becomes `{type: 'object'}`. A call to an integration that has no catalog yet says that the list did not come, and why the integration is not connected, instead of "no integration tool is named".
- **The risk map is read by own keys only**, so a tool named `constructor` or `__proto__` gets the default risk.
- **The redactor keeps the two newest values of each source.** `registerSecret(value, source)` drops the forms of older values of that source (a credential reference; the access and refresh token of an integration). Each OAuth refresh added up to eight forms before, and `redact` makes one pass for each: after 100 refreshes one redaction of a 200-tool list took 488 ms instead of 15 ms (now 17 ms). A value without a source stays for the life of the process. An old token is not removed from text that was already written, and it never was in a trace row, because headers are not recorded. The value before the newest stays (decided in the third verification round of M3): a Google request that left with the old access token can still be open after a 401 on another request refreshed it, and an error that quotes its authorization header was stored and logged unredacted.
- **The process tree of a stdio server uses start times.** Windows keeps the parent pid of a process after its parent ends and gives the freed pid to new processes, so a server with a reused pid listed unrelated orphans (for example `explorer.exe`). A descendant now counts only when it started after the server and after its parent, under a root that this process started; after the close the list is read again, and only a pid with the same start time is ended. A Job Object would be exact but needs native code.
- **The crash sweep reads a mark, not the clock.** The row of a tool output with effect `none` gets the stored outcome `unsent` (the dashboard word too), and the sweep skips only such rows. Comparing the row time with the start mark made a finished call look interrupted after the clock moved back.
- **A sign-in link shows only while the callback listens.** The SDK makes a flow when a sign-in stops in a call or a start that the owner did not begin, but the callback listens only during Connect, so that link ended in a refused connection with the code spent. The page offers Connect instead.
- **Refreshed tokens that the credential manager did not take stay in memory** and are saved again at each read until a save works. A server with rotation had spent the old refresh token, so the lost set ended the sign-in at the next refresh. A restart before the save still loses them. A failure of the credential manager inside a call is `not_sent` (its own error type), because the server did not accept the request.
- **The error of a connection attempt is redacted** before it reaches the state, `integration_state.lastError`, the page and the answer of Connect. A server that quoted its key put it there in plain text.
- **Requests from a server have a trace limit** of 100 a minute, like notifications; the answers of the app to the others are left out too, with one row that says so. 20,000 pings gave 40,005 rows and held the event loop for 50 s; now 206 rows and 1.3 s, the same as without the recorder. The client still answers every request.
- **A 401 or a 403 is an answer, not `unsent`.** The HTTP transport posted the whole call before the status, so the row is an in row with `{httpStatus, error}`. The outcome stays `not_sent` for the model, because the server refused before it acted. An auth error of the SDK (it comes only after a 401, or a 403 for a scope) gets the same row without a status; a credential manager failure keeps only the out row, because it can come before or after the post.

### 3.10 Decisions from phase 2 M2, verification round 4

- **One walk of the tool list at a time.** Each `list_changed` started a new walk after its debounce, also while an earlier walk or the first one ran. A slow, older answer then replaced a newer catalog (and was stored as the newest version), and a server with 64 pages of 9 MB and a `list_changed` each second filled the heap until the app crashed in 145 s. Now each attempt runs one walk, the first walk counts as one, and a `list_changed` during a walk runs one more walk after it. The same server now stays connected with the heap under 600 MB. A sequence number on each walk was not taken: it keeps the order, but not the number of walks. No cap on the bytes of a walk: the page limit and the message limit already bound it.
- **`nextCursor: null` ends the walk**, like a missing cursor. The strict cursor schema threw the whole list away.
- **An HTTP answer has the 10 MB limit of stdio.** A fetch wrapper on every HTTP entry (no auth, bearer, OAuth) stops a body over the limit and closes the transport, so the call is `unknown` and the backoff starts, as an oversized stdio line does. An event stream can stay open for hours, so there the limit applies to each event (a blank line ends an event; the data lines of one event count together). A 200 MB result now costs no blob and no trace row of its answer.
- **The reason that a tool list is missing is outside text.** It quotes the error of the connection, which can be the server's words. It now carries the untrusted source of the integration (so the session is tainted and the model reads it wrapped), and its trace row has `source = 'mcp'` and the integration. Dropping the error from the text was not taken: the error tells the owner what to fix.
- **A Pause during a Reconnect wins.** The reconnect checks the pause after the old connection closes and does not start. The answer of Connect says that the owner paused it. One queue per integration for pause and connect was not taken: one check closes the window.
- **The page gets a redacted catalog.** `status()` redacts the tools, the rejected tools and the hidden names, as the stored copy is.
- **The time of the newest message is the newest row by id**, one entry of the `(serverId, id)` index. `MAX(createdAt)` read every row of the server (0.6 s for 1.8 M rows at each load of the page).

#### 4.2.1 Decisions from phase 3 M1

The owner guide is `docs/setup/slack.md`.

- **Slack is config on the M2 layer.** Each workspace is one `mcp-http` entry with its own app and `clientRef`. Sending needs no new code: `slack_send_message` is `external` (also by default, because it has no `readOnlyHint`), so the owner approves every send, and a session that read Slack asks even when an allow rule matches. With `read` in the test config the acceptance send test fails, so the guide insists on `external` and keeps the schedule, draft and canvas tools out of `tools.allow`. There is no change to the registry, the approvals or the policy.
- **Paste callback.** Slack's documentation says that a redirect URL must use https, and the M2 callback is plain http on loopback. `auth.callback: "paste"` makes the redirect `https://127.0.0.1:4318/oauth/callback`. Nothing answers there with TLS, so the browser shows an error page whose address holds `code` and `state`; the owner pastes it on the Integrations page, and `POST /api/integrations/callback` gives it to the existing callback handler, which picks the flow by `state`, uses it once, and accepts it for 10 minutes. The default stays `loopback`. A local https server with a self-signed certificate was not taken: it needs certificate code and still shows a browser warning. Neither path is checked against real Slack.
- **Two M2 OAuth bugs, fixed for every integration.**
  - The provider read the SDK's copy `<id>:oauth-client` before `auth.clientRef`. The SDK writes that copy only to add its issuer stamp, so a client that the owner stored again later was hidden for good. With `clientRef` the provider now reads only that ref and never saves a copy; the issuer stamp stays in memory (without it the SDK warns at every sign-in).
  - The SDK takes the `scopes_supported` of the server metadata before the client's scope, so `auth.scopes` had no effect, the app asked for every offered scope, and an app that lacks one is refused. The sign-in link now gets the configured scopes.
- **Token errors with HTTP 200.** Slack answers a failed token request with HTTP 200 and `{ok: false, error}`. A wrapper in the sign-in fetch (`oauth-errors.ts`) turns that into HTTP 400 in the RFC form: grant codes (`invalid_refresh_token`, `invalid_code`, …) become `invalid_grant`, so the SDK clears dead tokens and the owner hears once; client codes become `invalid_client`; `ratelimited` and the codes of a server that is down become `temporarily_unavailable`, so the M2 outage rule keeps the tokens. The description is "the server said <code>", so `lastError` names the Slack code. A server that follows the RFC never sends `ok: false`, so nothing changes for it. A lift of a token under `authed_user` was not added, because nothing shows that the MCP token endpoint answers in that form.
- **The client is stored from the dashboard.** PowerShell drops the quotes of a JSON `/pass:` value before `cmdkey` gets it, so the M2 advice could not store a JSON client. `POST /api/integrations/:id/client {client_id, client_secret}` writes the JSON under `clientRef`, refuses extra keys and values with spaces, and answers only `{stored: true}` or an error. A text form `id:secret` was rejected as a second parse rule for one value. Connect with a `clientRef` and no stored value answers what to do and sends no request; a failure of the credential manager is not "missing". A stored value that is not JSON gives an error that names the ref and never quotes the value, and the client secret goes to the redactor. This closes the M2 gap "No UI to store a pre-registered `clientRef`".
- **The DM poll is a system automation** (`integration_poll`, every 15 minutes, created by `syncPolls` at start, like the heartbeat). The scheduler gives the claim, backoff, history, Run now, and "off after 5 failures, with one owner message"; the poll has no timer, claim or failure count of its own. A poll that the owner or the scheduler turned off stays off; the automation of an entry that lost `poll` is turned off, and it is turned on again when the entry gets `poll` back (the setting `polls-synced` keeps the ids that had a poll at the last start, like the heartbeat's synced value). Only the process that connects has polls (`JobDeps.polls`, keyed by integration id, so the Google poll can register the same way); in `npm run chat` the job is `skipped` (since the merge of phase 2 M3, chat does not claim it, see 4.9). An own timer was rejected (the scheduler tick already wakes each minute), and so were a poll run with `tool_calls` rows (about 96 rows a day per workspace in the Runs list, with no policy decision behind them) and an own cursor table (three values fit in one setting).
- **The poll algorithm** (`src/integrations/slack-dms.ts`). It reads the owner's user id once (`slack_read_user_profile`), then calls `slack_search_public_and_private` with `channel_types: 'im,mpim'`, `sort: 'timestamp'`, `sort_dir: 'asc'`, `limit: 20`, the exact second in `after`, and `filters: 'after:<utc day, two days before>'`, because the search needs a word or a filter. Slack reads that day in the user's time zone and gives only the later days; west of UTC the local day can be one day before the UTC day, so the first margin of one day left out the user's evening (a DM at 18:10 in Los Angeles never came back, and a later DM moved the position past it). Two days cover every time zone, and `after` still gives the exact second. It pages by keyset on the Slack `ts` (no server cursor): at most 10 pages, a day back at first, then from the position minus a 10-minute overlap for a late search index. A poll that stopped at its page limit sets `complete = false`, and the next one starts at the position without the overlap, or a burst inside the overlap would hold the poll for ever. A full page inside one second moves to the next second with a log line. Each page and the new state (`settings['slack-poll:<id>'] = {position, complete, selfId}`) are one transaction. A `ts` later than the clock never moves the position; that item is still stored as untrusted text. A margin of 10 minutes was tried first, but it equals the overlap, so a forged `ts` inside it removed the overlap of the next poll and a late DM was lost. A full page that is not ascending fails, because an older DM could hide behind the next page.
- **The poll fails closed.** An answer that the reader cannot read, a tool error, a refused or unanswered call, an unsorted full page, or a store error makes the job `failed` and keeps the position, so a new answer form stops the signals but never loses a DM without a message. The text of a DM must never cause such a failure, because the position does not move past it and every later poll fails on the same page. Not connected and not sent are `skipped`: they are connection states that the Integrations page shows. The error names the tool and the call id and never quotes the answer, because the scheduler puts it in `automation_runs` and in the owner's message; the log line may hold the first 200 redacted characters. Each call goes through the connection with `runId: null` and its own `poll:<id>:<uuid>` call id, so `mcp_messages` keeps every request and raw answer.
- **The reader** needs only `channel` and `ts` of each message: structured content, then JSON text (a list under `messages`, `results`, `matches` or `messages.matches`, the form of the `search.messages` Web API), then markdown. JSON without a known list is unreadable; it never goes to the markdown reader, which would see one message. "No results" or empty text is an empty page.
  - **Markdown is split only at the server's result headings.** The text of each DM is inside the answer, so a split at every heading or rule let one DM cut a message (its text after a `---` was lost), add 20 blocks with old `ts` values (the full page was "unsorted" at every poll, and the poll stopped for good), or add a block without a channel (the same stop). The first heading before any `ts` gives the form, for example `### Result 1 of 20`; only a line of that form whose first number is the next one starts a block, and every other line is text. A count before it ("Found 3 results") must equal the number of blocks, and no block starts after it. In each block the labeled `ts`, the channel and the user are the first matches, because the server's fields come before the text, and a heading before the `ts` is unreadable (a heading of the whole page is not the form of a result). An answer without a numbered heading, as a numbered list, is unreadable. **A DM can still hold a line of the result form** (pasted, or hostile), and then the reader cannot tell its false blocks from the real ones: a run of headings without fields made every block check fail, so the page failed at every poll and the position never moved (a stop for good); false blocks with fields and rising `ts` values up to the clock on a full page moved the keyset start and the position to the clock, so every real DM after that page was skipped, and the false blocks became signals in other people's names, also as the owner's `dm_reply`. Only the first block is certainly the server's, because its heading comes before the text of any DM. So a page with more lines of the result form than blocks, or with a later block that is not whole, gives only its first message (`onlyFirst`), and the next page starts in the second after that message. A false block is never stored, never moves the position and never pages, and the poll steps past the DM one request at a time. Without a count line, the page has at most 20 blocks. Rejected: a block start only where the server's field lines follow the heading (a DM can write those lines too, so it stops only the run without fields), and failing the page with the position kept (that is the stop for good again). The ids need a digit and are matched without the `i` flag, so a name such as "Christopher" or "dev2026team" on the channel line is not the id. The answer form of the official server is not documented, so the guide asks the owner to save the first real answer as a fixture before anything builds on the signals.
- **Signals.** Migration 008 creates `integration_events` (dropped by 006 because nothing wrote it) with `untrustedSource`, `occurredAt` (`occursAt` since migration 010, see 4.9) and `handledAt`, and a unique index on `(source, account, externalId)` with `account NOT NULL`. A Slack row has `source = 'slack'`, `account` = the integration id, `externalId = '<channel>:<ts>'`, `kind = 'dm'` or `'dm_reply'` (the owner's own message, kept for a later "unread for 4 hours" detector), a redacted summary of at most 300 characters, and the redacted text in a blob. Nothing reads the rows yet; a reader must wrap each summary with `wrapUntrusted(untrustedSource, …)` and carry the taint.
- **Fallback.** A documented `mcp-stdio` entry, `slack-mcp-server@1.3.0`, with an `xoxp` token that `cmdkey` can store. It has no poll in M1: a parser for an answer that no test has seen would double the poll code. Add it when the owner runs the fallback and a real answer exists.
- **Deferred.** A note on the send card with the name behind a channel id: a real safety gain, but it changes the `Tool` interface, the registry and the approval flow while the telegram and review branches change them, and the name is text that any Slack user chooses. Propose it after telegram M4 merges, with the card's invisible-character check applied to the name.
- **Known gaps after phase 3 M1.**
  - The answer forms of the official server, its redirect rule, and its token answer are unchecked (see the guide).
  - A DM that the search index shows more than 10 minutes late is missed. More than 20 DMs in one second skip the rest of that second.
  - A DM that starts its page and writes the next result heading makes the page give only its first message, and the next page starts in the next second, so a later DM in the same second is skipped (the log says so). See 4.2.2. If the real answer has no count line, a DM can still add whole false blocks while the page stays at 20 blocks or fewer: they become signals in other names, and when they make the page full, they move the next page as before. The fake has the count; the real form is unknown. A reader of the real answer form (the fixture) is the fix.
  - A Slack outage with tool errors for about 20 minutes turns the poll off until the owner turns it on again.
  - With a `clientRef`, the M2 copy `<id>:oauth-client` of an older install stays in the credential manager, unread.

#### 4.2.2 Decisions from phase 3 M1, verification round 3

- **The search asks for messages only** (`content_types: 'messages'`). The official tool also gives files; a file result has no message `ts`, so one file shared in a DM failed every poll until the scheduler turned the poll off. The fake now gives files unless the field leaves them out.
- **A false block is found, not guessed.** Round 2 gave only the first message of any page with more lines of the result form than blocks, and the next page started in the next second. So one pasted line such as `### Result 7 of 9` skipped the other DMs of that second, and a burst of such DMs moved one DM per request (200 DMs took 23 polls). Now the reader counts as false only what can be false: a line of the form with the next number starts a block, so a false block exists only when a later real heading lands in text with a number that is not after the blocks so far. The count, or else the limit of the page, stops any block after the last result. A line with a later number is text. A page with such a pushed heading, or with a later block that is not whole, gives its first message and `suspect`, the first block that can be false. The poll then asks again from the same start with `limit` at most `suspect - 1` and at most half of the last limit, so the DM with the false lines becomes the last result and its lines become text. When only the first block is whole, the next page starts in the second after it. The 200 DMs now take 8 polls or fewer, and the DM in the same second is read. A page with a false block still counts as full, so a poll that ends on one starts the next poll at the position without the overlap; with the overlap, a burst larger than one poll would be read again at every poll and never end. Rejected: the tool's `cursor` (the place and form of the cursor in the answer are not known, and a cursor in the text of a DM could be taken), a one-second window with `before` (the same page comes back), and reading the prefix before `suspect` as true (whole false blocks can stand there).
- **The sender and the channel come only from the field lines.** The reader took the first bare id anywhere in the block when the server's `From` or `Channel` line had none, so a mention of the owner in a stranger's DM made a `dm_reply`. Now the first line with the label gives the id, or nothing: a user line with a name or a bot id gives no user (`dm`), and a channel line without an id makes the block not whole.
- **A poll call waits one minute.** `callTool` takes an `answerWaitMs` option, and the poll passes `POLL_ANSWER_WAIT_MS` (60 seconds). With the 60-minute tool-call wait, a server that never answered held the poll for an hour while the scheduler started the next poll beside it. Eleven calls of one minute fit in the 15 minutes between polls.
- **Storing a client id without a secret keeps the stored secret** of the same client id. The page never shows the secret, so an owner who entered only the id deleted it, and the next token request failed. A new client id is another app and does not keep it; a stored value that is not JSON gives an error.

#### 4.2.3 Decisions from phase 3 M1, verification round 4

- **A field is only at the start of a line, and its id is the one that ends the line.** The sender chooses the display name on the `From` line, and the server prints that name before `Message_ts`. A name such as `Pat ts 4000000000.000000` gave every block of that sender a forged `ts`: a full page of 20 such DMs was unsorted (every poll failed, then the scheduler turned the poll off), or, with a `ts` after the clock, the keyset start moved one second a page and every poll said `completed` without reading on. A name such as `U0OWNER0001` made a stranger's DM the owner's `dm_reply`. Now a label counts only at the start of a line, after markdown such as `- ` or `**`, and the id of a `Channel` or `From` line is the id at its end, as in `From: Name (U0...)`. A line whose last id is not at its end gives no user, and a channel line of that form makes the block not whole. This is a guess about the real form like the rest of the reader; the fixture decides.
- **A line in the form of the first heading is text.** The real heading 1 is the first heading, so a later `### Result 1 of 9` can never be a real heading that a false block pushed into text. It made the page give only its first message, and the poll moved past the rest of that second. Such lines no longer mark a block as suspect.
- **The refresh single flight reads only a form body.** It read every POST body as a form, also a JSON-RPC tool call, so two sends within 30 seconds whose text held `grant_type=refresh_token&refresh_token=x` became one request, and the second send got the first answer. A string body now counts only with the content type `application/x-www-form-urlencoded`; the SDK sends a `URLSearchParams` body.
- **A token without a configured scope makes a new sign-in.** Slack user tokens without rotation never expire, so after the owner added a scope to `auth.scopes`, Connect used the old token, Slack was never asked for the new scope, and the guide's fix for `missing_scope` did nothing. When the stored token names its scopes (spaces or commas) and one configured scope is not among them, the provider gives the SDK no token, so a sign-in link waits. A token without a scope field is kept. A "sign in again" button was not added: the config is the owner's statement of what the token must hold.
- **Known gap.** A DM whose text holds a line of the result form with a number from 2 up to its own place still makes the page give fewer messages. When the smaller page is full inside one second, the poll moves past that second, and a later DM in that second is skipped (the log says so). A real heading that a false block pushed into text looks the same, so the reader cannot tell them apart without the real form.

#### 4.2.4 Decisions from phase 3 M1, verification after the merge

- **The scope check uses the scopes that the last sign-in asked for, not the granted ones.** OAuth lets a server grant fewer scopes than asked, for example when a workspace admin restricts one. The check of round 4 then refused every token: each sign-in said "Connected", and the integration stayed `needs_auth`. The stored token JSON now also holds `requested`, the configured scopes at its code grant, and a refresh keeps it. A new sign-in starts only when a configured scope is not in `requested`. A token from before this record uses its `scope` field once, so the next sign-in writes the record. When the grant lacks a configured scope, the sign-in page and `lastError` on the dashboard say "Connected, but the server did not grant these scopes: ...", and the integration connects with the token. Rejected: keep only the `lastError` text without the record, because a token that never expires would then hide a scope added to the config later.
- **A configured scope entry is split on commas and spaces, like the record.** Slack writes scope lists with commas, and an entry such as `"search:read.im,search:read.mpim"` could never match the split record, so each sign-in said "Connected" and then asked for a new one. The split list is used for the authorize request, `requested` and both checks. Rejected: refuse such an entry in the config schema, because the split is one line and an owner who copies a list from the Slack app page gets a working config. The provider also keeps the last known `requested` in memory, so a refresh whose read of the stored tokens fails still saves the record; without it a withheld scope would refuse the new token after the refresh, and with rotation the old refresh token is already spent.
- **The owner's Connect signs in again when the token lacks a granted scope.** With `requested` alone, a scope that the admin allows later could never reach the token: Connect and restarts reused the token, because `requested` already named the scope. During an owner's Connect, the provider now gives the SDK no token when the token's granted `scope` lacks a configured scope, so a sign-in link waits. A start or a call by itself keeps the smaller grant, so the app does not make a link again and again while the admin still refuses. Cost: a Connect that the owner presses for another reason while a scope is withheld also asks for a sign-in; the connection keeps the stored token while that link waits (section 4.2.5). Rejected: a separate "sign in again" button (one more control for a rare case), and only telling the owner to delete the tokens with `cmdkey` (a manual step in the credential manager).
- **The withheld scopes are a field of the status, not only `lastError`.** The provider computes them from the stored token at each read and save, and the Integrations page shows them as "Not granted". The next error overwrites `lastError`, and a crash between the token save and the database write lost the text.

#### 4.2.5 Decisions from phase 3 M1, verification round 4 after the merge

- **A Connect that only asks again keeps the connection.** The forced sign-in gave the SDK no token, so the connection stopped at `needs_auth` while the stored token still worked: tools gave `not_sent`, DM polls were skipped, and nothing reconnected after the link expired. When the forced start ends with a waiting link and the stored token lacks a configured scope, Connect starts the connection again with the stored token and returns the link. The link still finishes a sign-in; until then Slack and the DM polls run with the smaller grant. Rejected: only document the gap (Connect is also the resume action, so a resume would stop Slack), and fall back to the token when the link expires (up to 10 minutes without Slack).
- **A refresh answer without `scope` keeps the scope of the stored token.** RFC 6749 section 5.1 lets a server leave `scope` out when it does not change. The record of the withheld scopes then went at the first refresh, and Connect never asked again for a scope that the admin allows later. A refresh (no active flow) now keeps `scope` from the stored token, as it keeps `requested`. A code grant without `scope` keeps none, because a new sign-in can grant other scopes. Not checked against real Slack: whether its refresh answer names `scope`.

### 4.3 Web search and fetch

No paid search API. The owner has Chrome on this PC, and search runs through it.

- `web_search { query, engine? }`: the browser worker (section 4.4) opens the engine's results page in the agent's Chrome profile and extracts the result list (title, URL, snippet) from the page. The default engine is Google. DuckDuckGo's HTML results page is the fallback when Google shows a CAPTCHA or a consent wall. Keep the volume personal-scale (a few searches per task), and back off when an engine shows a CAPTCHA. A self-hosted SearXNG container is an optional extra later; it is also free.
- `web_fetch`: a local fetch with readability extraction, a 20,000-character limit, results through handles, and `wrapUntrusted`. Pages that need JavaScript or a login go through the browser instead.
- **Exfiltration guard.** In a tainted run, a fetch URL that contains data from the run (long query strings, encoded text) goes to the reviewer.

### 4.4 Browser

**Decision:** Playwright as a library, in-process (`playwright` 1.64.x). It runs the installed Chrome (`channel: 'chrome'`) with a dedicated persistent profile at `data/browser/profile`. This is the owner's real Chrome program with a separate profile, so pages, search engines, and logins behave like normal browsing. The owner's everyday profile, with banking and every other session, stays out of reach. The library gives the hard controls we need: a route-level domain allowlist, a screenshot and accessibility snapshot after every action, and Playwright tracing. These are things the MCP server flags do not enforce as a security boundary.

- **Tools**, shaped like the snapshot-based browser tools models already know:
  - `browser_open(url)`
  - `browser_snapshot`
  - `browser_click(ref)`
  - `browser_type(ref, text)`
  - `browser_select(ref, value)`
  - `browser_back`
  - `browser_screenshot`
  - `browser_extract(instructions)`: returns text through a handle.
- **Browser worker.** Browser work runs in a sub-agent with the `browser` profile (section 6), so page content never floods the main conversation. The worker returns a summary.
- **Allowlist.** Each task gets a domain allowlist: the start domain plus domains the owner approved. Navigation outside it is blocked, and the block is recorded.
- **Profile hardening:**
  - password saving and every kind of autofill are off;
  - downloads go to `data/browser/downloads`;
  - the owner logs in to the sites the agent may use by running the browser in headed mode (`okc browser login`).
- **Risk:** navigation and reading are `read` (they taint the run). Typing into fields and clicking are `write` (the reviewer checks them). Submitting a form that sends, buys, or posts is `external`, with approval and a screenshot in the approval card.
- **Later:** a supervised "use my real Chrome" mode through `chrome-devtools-mcp --autoConnect`. Chrome then asks the owner to allow each session, so this mode needs the owner at the PC.

#### Decisions from phase 3 M2

- **Library.** `playwright-core@1.64.0` (it downloads no browser) drives the installed Chrome (`channel: 'chrome'`, headless) on `data/browser/profile`. One Chrome per process starts at the first use and closes after 10 minutes without a task. `npm run chat` never starts it. Chrome's own `lockfile` (`EBUSY` on Windows) is the profile lock; on macOS and Linux the lock is the `SingletonLock` symlink to `<host>-<pid>`, which is busy while that pid is alive (also when the check gets `EPERM`) or when the host differs, and free when the link is missing, the pid has ended, or it is a plain file. Both stay exact after a crash, so the app has no lock file of its own. Extraction uses `@mozilla/readability@0.6.0` on `linkedom@0.18.13`.
- **The gate has two layers and one `judge()`.** A Playwright route sees the first request of every tab, frame and popup, but not the hops of a redirect (a 302 from an allowed site reached the off-list site). A CDP `Fetch` session on each tab pauses every hop. A document (a page or a frame) must be on the task's allowlist. Every request needs a public address, checked in Node. No request with a body, and no request other than GET, HEAD or OPTIONS, leaves outside an approved `browser_submit`: form posts, a script's `fetch` or XHR post, beacons. A web socket needs the allowlist, like a document (a route on each tab; the context route refuses the sockets of every other page). GET subresources need no allowlist, because a page loads from many CDNs. The allowlist stops the agent, or an open redirect, from moving the tab to a new site; it does not stop a page script that puts typed text into the address of an image (see the known gaps), so each step records the hosts off the allowlist that its requests reached (`offsiteHosts`). A closed proxy with a bypass list was rejected: it breaks third-party subresources, restarts Chrome on each allow, and depends on undocumented Chrome behaviour.
- **`web_fetch`** uses `node:http` with a `lookup` that checks the address that the socket uses (no DNS-rebinding window), a separate check for IP literals (Node does not call `lookup` for them), redirects hop by hop (5 at most), and a 5 MB cap on decoded bytes. `isPublicAddress` refuses IPv4 inside IPv6 in every form (`::ffff:7f00:1`, NAT64, 6to4).
- **Each step is one record.** `act()` runs one action in a tab queue and writes a `browser_steps` row: the URLs before and after, the masked snapshot (a text blob), a JPEG screenshot at quality 60 (a byte blob, about a quarter of a PNG), console errors, blocked requests, and `sent`, the non-GET requests that a submit let out (once each, although both layers see the first request). The row has an index on `(runId, toolCallId)`, so the page joins each step to its risk, decision and approval. A blocked navigation of the page itself leaves Chrome on `chrome-error://`; the step waits at most 2 s for it and goes back to the page of the step start, or to the last page of the tab when the block came between two steps (a timed refresh replaces its own history entry), so the model never reads the error page and it never becomes a taint source.
- **Snapshots.** The `ai` aria snapshot shows password values in plain text, so each value is masked. `browser_type` refuses a password field, and `browser_submit` refuses a form that holds one; the owner signs in with `okc browser login` (a plain Chrome with `--user-data-dir`, because sign-in pages refuse an automated browser). Each ref carries its snapshot number (`s3e12`), and a ref of an older snapshot is refused: Playwright reads a ref against the newest snapshot, and a click can wait hours for the owner.
- **Refusals.** A refusal before any action (no Chrome, no task, busy, a stale ref, a password field, a click on a control that sends a form) has `effect: 'none'`. A submit whose page differs from its input sends nothing but keeps the effect unknown, so the approval does not go back to pending with an input that fails again. Each refusal names the next allowed move.
- **Tools and ownership.** 10 browser tools: `browser_open`, `_snapshot`, `_back`, `_extract`, `_close` (read); `_click`, `_type`, `_select` with `{ref, element}` (write); `browser_submit {url, button, fields}` (external, checked against the live page); `browser_allow_domain {url, domain, reason}` (external with `needsApproval`, so a broad allow rule never lets the agent widen its own allowlist). `browser_screenshot` was dropped: every step has a screenshot, and a tool result is text. One task runs at a time, owned by its session; another session gets "busy" until the idle close (a 60 s takeover was removed, because it closed a page whose submit waited for the owner). `browser_submit` and `browser_allow_domain` act on the one open task, whichever session started it, and check the URL in their input: a `browser` child session cannot get approvals, so its parent sends the form. `BROWSER_OWNER_TOOLS` and `BROWSER_PAGE_TOOLS` give the split for the M3 profiles.
- **Trace zip.** One per task, saved at close, crash or interrupt with time limits; `traceError` says why one is missing. `snapshots: { dom: false, aria: false, screen: true }`, because Playwright records the network log, with every cookie, only with DOM snapshots. A probe then showed that the trace also keeps the result of every call: the snapshot before the mask, the password values, and the HTML of `browser_extract`. These reads run in an internal API zone of the Playwright client (`_wrapApiCall(..., { internal: true })`), which the trace leaves out; the actions (`goto`, `click`, `fill`) stay. The zone is a private method, so tests pin that the zip holds no password, cookie or DOM that the app read. A zip rewriter was the other option (about 100 lines for a zip reader and writer). Console messages stay in the zip (see the known gaps).
- **Extraction stays in a worker thread.** On the main thread, pages inside the caps (depth 120, 20,000 elements) took 1 to 14 s (a list of 19,700 items under 117 levels: 14 s), and 5 MB of nested tags took 2 minutes. The worker has a 5 s limit and a linear tag-strip fallback. Readability's own `maxElemsToParse` never stops on linkedom (its `getElementsByTagName('*')` gives no element), so the depth walk also counts the elements.
- **Search.** Engines in order (Google, then DuckDuckGo HTML), one search at a time, a 2 s gap, at most 20 an hour per engine. A CAPTCHA pauses the engine for 15 min, 1 h, 6 h, then 24 h, and a consent page for 1 h; the state is in `settings` (`web_search.engines`), so a crash loop cannot hammer Google. The first launch in a process reads the user agent and starts Chrome again without `HeadlessChrome`.
- **Dashboard.** `mountBrowser` (`src/dashboard/browser.ts`) adds `GET /api/browser` (engine pauses, the profile lock, tasks with blocked and sent counts), the task detail, screenshots (only a blob that a step names, only `image/png`, `image/jpeg` or `image/webp`, with `nosniff` and `content-security-policy: default-src 'none'; sandbox`, because the sandbox files share the blobs table and an svg there can hold a script), and the trace zip at `traces/<taskId>.zip` only.
- **Verification round 1.**
  - `browser_submit` found its form by the text of the button, then clicked the button that `getByRole` found by its accessible name; a page where the two differ sent another form than the one checked. The check and the click now use one element handle, found by the accessible name, which is also the name in the snapshot. A button with an `aria-label` can now be sent.
  - Each action has a deadline (`navigation + 2 × action`). A read in the page (`count`, `evaluate`, `content`) has no timeout of its own and waited for ever on a looping page, which also held `browser_close`, the idle close and every later `web_search`. Past the deadline, the step is recorded and the tab ends as crashed; the search goes on to the next engine. The run signal is not passed into `inTab`, because the deadline already bounds each search.
  - The check and the start of a task run one at a time: two opens in one turn left a tab in no session map.
  - The lists of blocked and sent requests start again after each record, not at each step start, so a block between two steps goes into the next row.
  - `browser_open` takes the `web_fetch` shape check (no `chrome://`, `file:`, credentials). A first address or an allowed domain whose site is a public suffix is refused, and `www.` stays when no dot is left without it. The task row is still written before the first navigation: a failed first load keeps its allowlist, which the agent chose and which is no wider than a load that worked.
  - A fill whose text the redaction changes runs outside the trace; other fills stay in the action list.
- **Verification round 2.**
  - **A third layer: an address proxy.** A shared worker, a web socket of a dedicated worker and a speculation-rules preload belong to no tab, so neither page layer saw them, and they reached the owner's network. Chrome now runs with `--proxy-server` pointing at a proxy inside the app (`src/browser/proxy.ts`) and `--proxy-bypass-list=<-loopback>`, so loopback addresses also go through it. The proxy checks the address of each plain request and each `CONNECT` tunnel and connects to the address it checked, which also closes the DNS-rebinding gap. It knows the host, not the tab, so the allowlist and the rule for sending data stay with the page layers; a refusal goes into the blocked list of each open tab. This is not the closed proxy that was rejected above: it has no allowlist, so third-party subresources still load and an allow needs no restart. Other options tried: deleting `WebSocket` in each worker through CDP auto-attach loses a race, because Playwright resumes the worker first (a probe with an 800 ms delay let the socket through); `Network.setBlockedURLs` does not stop a socket; an init script cannot reach a worker.
  - **No shared worker** (`--disable-blink-features=SharedWorker`): its POSTs skipped the rule for sending data. **No preloading** (`net.network_prediction_options: 2`); behind the proxy Chrome already skips the preloads, so the test pins the pair.
  - **Submit.** The check reads `new FormData(form, submitter)`: no disabled field, every selected option, every value of a repeated name (`fields` takes a list for such a name). The card shows that set without the hidden inputs. While a submit runs, the gate compares the body of a document request (url-encoded, multipart or plain text) with the checked set and fails it when they differ, so a page that changes a field on `pointerdown` or `submit` sends nothing. Each `sent` entry keeps the first 2,000 characters of its body, redacted, and the Browser page shows them. A script's own `fetch` post during the submit is recorded but not compared.
  - **Records.** Password values are read in every frame. A close writes a last step row when a block, a send or an off-list host came after the last step. `urlBefore` and `urlAfter` are stored redacted, and an open, a select or a way back whose text holds a secret runs outside the trace. A tab whose task row fails closes, and the open gives a refusal.
  - **Failures.** `stripTags` is linear (an `indexOf` scan for tags and the title, one pass for white space), and the extraction runs it only when the worker gave no result. The search gap, the hourly count, the idle close and the gate's name cache use `performance.now()`; only the captcha pause uses the wall clock, because it is kept across a restart.
- **Verification round 3.**
  - **Unload posts.** A close (`browser_close`, the idle close, the app stop, a hung tab) ran the `pagehide` and `unload` handlers after the tab left the tab map, so the page layers no longer judged their beacons and keepalive posts, and the proxy (address only) let them reach any public host. `endTab` now moves the tab to `about:blank` (untraced, capture time limit) while the gate holds, waits 200 ms so the blocks are recorded, and then writes the `close` row. A `beforeunload` handler did not stop the move. A method check in the proxy was not added: HTTPS tunnels are opaque to it, and it would need the submit state of the tabs.
  - **Bounded lists.** A page that posts in a loop put 174,000 entries (293 MB) into one row in a minute. Each step keeps 200 blocked, 200 sent and 200 off-list hosts, with addresses cut to 1,000 characters; the row's last entry counts the rest, and the tool text gives the full count.
  - **Masks.** The snapshot trims a value, turns each run of white space into one space, and escapes a value in quotes, so a password with a space at its start showed in clear text. Each value is masked in its raw, shown and escaped forms. Masking by element was not built: Playwright keeps the ref of an element in internal state.
  - **WebRTC.** `webrtc.ip_handling_policy: disable_non_proxied_udp` in the profile stops STUN and connectivity checks with page-chosen text to this PC; the `--force-webrtc-ip-handling-policy` flag did not.
  - **Submit check.** Exactly one whole-number pair of each click-position name may leave (`go.x`, `go.y`, or `x`, `y` for an image button without a name, which now works); a form's own field of that name stays on the card. A multipart file part with content fails the check, because the agent cannot attach a file.
  - **Search.** A consent wall is read only from a blocked top-level navigation of the search tab to a `consent.` host, not from a proxy refusal that another task's page caused. A pause that ends more than the longest backoff (24 h) from now came from a clock that was ahead and counts as over; a pause that ends on another day shows its date. `okc browser login` ends every pause when its window closes and keeps the strikes; the dashboard uses the same `pausedNow`.
- **Verification round 4.**
  - **Submit.** The gate let data out only while the click ran, and the tool said "sent" when the page sent nothing: a form that a script sends after a wait, a form that opens a new tab. After the click the submit now waits up to 5 s for the first request that the gate lets out (not for a GET form), and stops early when the gate refuses the page's own send. With nothing sent, the tool says so and is an error; the effect stays unknown. While a submit runs, a request other than GET also needs the allowlist: a page answered the click with its own post, with other fields, to an off-list site. A script post to an allowed site is still not compared with the checked fields, because many sites send their forms that way; it is recorded with its body.
  - **The owner's own addresses.** A global IPv6 address of this PC is in no private range, and the router gives each device of the LAN an address of the same /64; `web_fetch` and a page reached a server on this PC that listened on `::`. `isPublicAddress` now refuses each address of this PC and the /64 of each of its IPv6 addresses, read from `os.networkInterfaces()` again after 10 s. Loopback and link-local interfaces are left out of that list, because a Node `BlockList` also matches an IPv4 address against IPv6 rules (`::ffff:a.b.c.d`), so the /64 of `::1` held every IPv4 address.
  - **Password mask.** Each form of each value went through the whole snapshot, and a page with 3,000 password values held the event loop for 246 s. One regular expression of all forms, the longest first, takes about 0.1 s for that page. Above 200 values the step gets no snapshot.
  - **Search.** A search opens its page outside the trace: the trace belongs to the context, so it kept the query of a search that ran while a task was open, with a secret in it.
  - **Capture limit 15 s** (was 5 s). A page with 10,000 table rows had neither a snapshot nor a screenshot in 5 s, which counts as a hung page, so its task ended. A hung page now holds its tab longer before it closes.
  - A `browser_open` that the allowlist refuses comes before Chrome, so no gate saw it. The next row of the task now lists it with the blocks.
- **Verification round 5.**
  - **Submit waits for the form, not for the first post.** The submit ended at the first request with data, so a beacon at the click, or a post to the site's own check before the order, ended it, and the gate then refused the form; the tool said "sent". The gate now marks the request of the form (`sent.form`): a document request with data (which already passed the check of the fields) or a script post whose body is the checked set. The submit waits up to 5 s for it, then keeps the gate open until the page sends nothing for 1 s (at most 10 s in all). No form request: an error that says the form was not sent, also when other posts left. The form left but a later request with data was blocked: an error, because the page may not have finished. The tool output and the Browser page label each sent request "the approved form" or "sent by the page". A fixed settle time alone was rejected: a beacon would still count as the form.
  - **A request with a body sends data**, whatever its method: `fetch` lets a page send OPTIONS with a body. OPTIONS was not removed from the methods that only read, because the gate also pauses CORS preflights, which have no body.
  - **The method of a submit is the browser's own** (`formMethod`, else `form.method`): `dialog` and an empty or invalid `formmethod` (which the browser sends as GET) are no longer treated as posts, so a click may press them and a submit does not wait for data.
  - **No secret in an address or a query.** Playwright records each console message with the address of its page, and the screencast of a traced context covers every page of the context, also a short search tab. An untraced goto therefore did not keep a secret in a `browser_open` address or a `web_search` query out of the zip. Both tools now refuse such text (`redact(text) !== text`) before any page opens, and the `error` column is stored redacted like the addresses. Searches in a second, untraced context were not built: a persistent context has no `Browser` to make one, and the search needs the profile's cookies. Stopping the trace chunk around a search would split a task's trace into several zips.
  - **Captcha text** counts only on a page without results: a results page shows the query, so a search about an "unusual traffic" message paused both engines.
- **Verification round 6.**
  - **Channels outside a frame.** Chrome's network service sends a report of the Reporting API with no frame, so neither page layer saw it: an https page put typed text into its own address and had a CSP report carry it to an off-list host. The features `Reporting` and `NetworkErrorLogging` are now off. Chrome uses only the last `--disable-features`, and a second list turned Playwright's own list off (a probe saw storage partitioning come back), so the first launch reads Playwright's list from `chrome://version`, and later launches replace it (`ignoreDefaultArgs`) with a list that holds both. WebRTC reached a TURN server over TCP through the proxy with typed text in the user name. No Chrome switch removes the API (`--disable-blink-features=RTCPeerConnection`, `WebRTC` and `--disable-webrtc` all leave it), so a context init script deletes `RTCPeerConnection` before the scripts of each document run, also in a frame that a script makes. A STUN check in the proxy was rejected: it does not see TURN over TLS.
  - **The proxy reports what it lets through.** A host that no open tab allows goes into `offsiteHosts` of each open tab, so a channel that no page layer sees (the socket of a dedicated worker, or a future one) shows on the Browser page. Chrome's own connections can show there too.
  - **Controls of a script.** A button outside a form that posts with `fetch`, or a `type=button` that calls `form.requestSubmit()`, could not send with any tool: the gate blocked the click, and `browser_submit` pointed to `browser_click`. `browser_submit` now takes any button. In a form, the check is the set of the form without a submitter. Outside a form the set is empty, so a form that its script sends is refused; the first request with data that the gate lets out counts as sent, and the result lists each request with the start of its body. A password field with a value anywhere on the page refuses such a send.
  - **`browser_submit` has `needsApproval`.** It acts on the open task of any session, so the caller can be a session with no taint (an automation, or main after a reset), where a broad allow rule such as `browser_*` holds.
  - **The idle close waits.** A tick during `newPage` closed Chrome under it, and the open, and every later open and search, hung until a restart. A tick during a close lost the task's trace and left its id in `tracing`, so no later task got one. A launch while the closing Chrome still held the profile was refused as "in use by another Chrome window". A counter now marks the work that starts or ends a tab, and the idle close skips while it is set; a launch waits for the idle close to finish; `tracing` is cleared whenever the context closes.
- **Verification round 7.**
  - **Controls that are not buttons, and frames.** `browser_submit` looks for a button, a link or a menu item of the name in each frame of the page, and takes the address of the page or of the frame. An ASP.NET postback link sets a hidden field and then sends the form, so for a control that is not a submit button the check leaves the hidden fields of the form out of the comparison; a changed field that the owner reads is still refused, and the data still goes only to the sites of the task. A select that sends its form on change is not covered.
  - **Legacy encodings.** The check reads the encoding of the form (the first known `accept-charset`, else the page, utf-8 for utf-16), and the gate decodes the percent escapes and the multipart bytes in it. A character that the encoding cannot hold leaves as `&#N;`, so both sides are compared with the references read. A body that matches in utf-8 also passes, because a script sends `FormData` in utf-8.
  - **The sent record.** Each layer of the gate counts the requests with the same method, address and body; a request adds an entry when one layer saw it more often than the other. A key of the method and the address alone dropped a second post with other data. Request ids were not used: the CDP id and the Playwright request cannot be joined.
  - **Dialogs.** Playwright dismissed each dialog, so an approved form that asked `confirm()` was never sent. A dialog during an approved submit is accepted, a `beforeunload` dialog is accepted so the agent can leave the page, and other dialogs are dismissed. Each step names its dialogs in the result and in the console list.
  - **Smaller fixes.** The Browser page counts blocked requests, not steps with a block (the overflow entry of a step counts as one). `web_fetch` reads a page with no content type as HTML when it starts with `<!doctype html` or `<html`, and a byte order mark wins over the declared charset.
- **Verification round 8.**
  - **Submit results that match what left.** A single-page shop stops the submit and posts the fields as JSON, which the gate cannot compare with the form; the tool said "not sent" for an order that had left, and a retry could order twice. When the form did not leave as a form but the page sent data that the gate let out, the tool now names those requests and says to check the page before a second send. The click no longer waits for its navigation (`noWaitAfter`), because a site that answered after the action timeout gave a click error for a sent form. After the form left, only a refused page navigation counts as "the page may not have finished": an analytics beacon of the thank-you page to an off-list host is still listed in the step, but it no longer makes the order an error.
  - **`browser_submit` takes an optional `ref`.** A product grid has an "Add to cart" in each form, so the name alone matched more than one control, and no tool could send any of them. The ref picks the control, and the control must still have the name that the card shows.
  - **Chrome that stops answering.** The start of a tab has a time limit; a Chrome that does not answer closes, and the next call starts a new one. A launch that fails closes each Chrome that it started, so the profile lock does not stay with a lost Chrome. The launch removes the service worker registrations of the profile, because a worker that a site registered in `okc browser login` sent its own requests outside every tab. The raw trace goes to `data/browser/tracing`, not `%TEMP%`, and each saved zip and each launch empty that folder.
  - **The proxy answers 502** for a server status line that Node reads but `writeHead` refuses; the throw ended the app.
  - Not fixed: a PDF has no reader (`web_fetch` says "not text", and the gate blocks the built-in viewer).
- **Known gaps after M2.**
  - A `web_search` that runs while a task is open shows in that task's trace: frames of the search page and its console messages, with the query.
  - Redirect hops inside a cross-site iframe run in another CDP target and are not checked; the first hop of each frame is.
  - A tainted session can carry data out through a GET: the URL of `browser_open` or `web_fetch`, or a GET form on an allowlisted site. This is M3's exfiltration guard and reviewer. Until then the owner approves each click and type, or adds a rule (`docs/setup/browser.md`).
  - A page script can send text that the agent typed to any public host in the address of a GET subresource, with no submit. The step records the host (`offsiteHosts`), not the address. Approving a `browser_type` therefore means that the text can leave the PC. A web socket of a dedicated worker skips the socket route of the tab: the proxy keeps it off the owner's network, but it can reach a public host off the allowlist. The proxy records its host on the steps of each open tab, not its address or its data.
  - The owner's own network is the private ranges, each address of this PC, and the /64 of each IPv6 address of this PC. A LAN with more than one /64 (a delegated /56) has other subnets that count as public.
  - Public suffixes: a two-label rule (a generic name such as `co` or `com` under a country code) and the one-label case only; no full suffix list, so a hosting suffix such as `github.io` can still be an allowed domain if the owner approves it.
  - Card numbers and one-time codes in fields that are not passwords are not masked. Screenshots are not redacted.
  - The HTTP proxy does not carry UDP. WebRTC is removed from each page (round 6); WebTransport (HTTP/3 over UDP) was not probed. A button outside a form sends what its script chooses to the sites of the task; the owner approves the button, not the data, and reads the sent bodies afterwards. An address with a secret that a page itself navigates to (a redirect, a script) still shows in the trace's navigation events.
  - The trace keeps the console messages of a page. Playwright records them on the server side with no option to leave them out, so a page that logs its password value, `document.cookie` or its HTML puts them into the zip. A rewrite of the zip after the stop was not built (same reason as above); the owner guide says so.
  - Client hints (`Sec-CH-UA`) over HTTPS can still name the headless brand; real Google and DuckDuckGo markup and bot detection are untested by rule.
  - An approval after a restart sends nothing; the agent must open the page again. The idle close skips a task while a `browser_submit` or `browser_allow_domain` approval from that task waits (pending, or approved and not yet started), so the 24-hour approval expiry bounds it (final review 2).
  - The `lockfile` lock and the `SingletonLock` link, `chrome-error://`, the CDP `Fetch` hop pause and the internal trace zone are behaviours, not API contracts. Tests run against the installed Chrome and the pinned Playwright, so a change breaks a test.
  - Downloads are off in the agent's browser (`acceptDownloads: false`); the owner's `okc browser login` window saves them to `data/browser/downloads`. Traces and screenshots grow until `okc prune`.

### 4.7 Decisions from phase 2 M3

Three designs were built and judged (minimal, failure modes first, owner experience first). The build takes the failure-mode design as its base and adds parts of the other two. The owner guide is `docs/setup/google.md`.

- **Library.** `@googleapis/gmail@22.0.1`, `@googleapis/calendar@20.1.0` and `google-auth-library@11.3.0`, pinned exact. This is the code of `googleapis` (4.1) at 2 MB instead of 245 MB. The SDK retries are off (`retry: false`; one 503 was four requests), each request has a 30 s timeout, the token requests have the same timeout and no library retries (a token endpoint that never answered held a poll for about 15 minutes), and the OAuth client runs with `forceRefreshOnFailure`, so the token endpoint decides a 401: `invalid_grant` is a dead sign-in, a 5xx is an outage. Only errors with the gaxios symbol become a `GoogleError` (`kind`, `status`, `reached`) with a redacted message of at most 300 characters; the SDK error carries the request config and can quote `Bearer …`. A failed token request never reached the API, so its effect is `none`.
- **Config.** A `google` block in `okc.config.json` (`clientId`, `accounts: [{alias, email?}]`, `send = false`, `sessions = ['main']` with `auto` or the read-only `auto-read` for automations, `pollMinutes = 15`), not a `builtin` entry in `okc.integrations.json` (3.2). That file and its manager assume MCP: `tools.allow`, a connection and a catalog. Without the block nothing changes: no tools, no automation, no prompt text.
- **Pinned tools.** 14 tools `google__*` (13 without `send`) with zod schemas in code, in the `tools` parameter of the sessions that `sessions` names. This is group 2 of 3.4. The list depends only on the config, so it is byte-stable in a session, and no untrusted catalog taints the session. `account` is an enum of the aliases, plus `all` for reads.
- **Secrets.** The client secret (`google.client`) and one refresh token per alias (`google.<alias>`) are in the Credential Manager through `SecretStore`. Access tokens stay in memory. Each value is registered with the redactor under its own source, and `registerSecret` also registers `encodeURIComponent(value)`: a token endpoint that quoted its form body put `1%2F%2F…` in the log. The owner uploads the client file on the Google page; the server checks the client id against the config and keeps only the secret.
- **Token health.** `invalid_grant` and `unauthorized_client` (a refresh token that another client issued) park the account (`needs_auth`); tokens are never deleted, and a parked account makes no request. The owner gets one message, by a compare-and-set on `alertedAt`, also over a restart and three calls at once. `invalid_client` parks every account with one message that names the client, and a new client file lifts that park without new sign-ins. A poll that is still at work when the client is refused keeps the reason of the park (its next request fails with "sign in again", and that text replaced the reason, so the account stayed parked), and the new client file also resets the failure count. After 12 failed polls in a row the owner gets one stall message. The poll job always returns `completed`, so the scheduler never turns it off.
- **Sign-in.** An ephemeral loopback port (never 4318) that listens only while a flow waits, PKCE, a one-time `state` for 10 minutes, `login_hint`. A wrong account or a missing scope revokes the new token, keeps nothing, and says what to do in words. The Gmail baseline is taken at the sign-in, and a cursor that exists stays, so the mail of an outage is still news after a reconnect.
- **Gmail sync** has two phases. `history.list` (at most 10 pages) inserts the new inbox ids as `state = new` and moves `google_accounts.historyId` in one `BEGIN IMMEDIATE` transaction with a compare-and-set. Then at most 50 rows per account and poll are read with `messages.get(metadata)`, each on its own. A 4xx for one message skips that row when Google gave another row of the same poll; a 4xx for every row keeps them, because it can be about the account. A crash or a failed page loses and repeats nothing; the unique key is the guarantee, and the compare-and-set only stops a slow poller from moving the cursor back. A 404 history id runs `getProfile`, then `in:inbox newer_than:2d`, and the note of the poll run says so.
- **Calendar sync.** The first read uses `timeMin = now − 1 day` and `singleEvents`, later reads the `syncToken` with the same `singleEvents`; the token moves after the signals of the last page are stored, and a 410 reads again without signals. A read stops after 20 pages and keeps its position (`calendarPage`: the page token, and the `timeMin` of a first read), committed with the signals of each page, so the next poll goes on from it. A refused page token is dropped. The live range for the detectors is read after any failure of the poll, also of the mail phase: the date detector checks each mail one time, and one failed message read made a permanent false hit. The change list is read after a mail failure only when Google answered and the fault is not about the account (auth, client, rate). Only changes by others (`organizer.self !== true`) are signals (`invite` or `event_change`, keyed `eventId@updated`). There is no copy of the calendar, so a cancelled event without an organizer makes no signal. The copy was rejected: it drifted from Google for recurring and deleted events, and its unbounded first read did not finish on a large calendar.
- **Signals** (`src/signals/`, source-agnostic for Slack). `integration_events` has `state`, `label`, `labelAttempts`, `labelModelCallId`, `detectors` (null until checked), `runId`, `handledAs` (`notified | seen | filtered | stale`) and `handledBy`, unique on `(source, account, externalId)`.
  - **Detectors run first**, so a label never hides a hit. `date_not_on_calendar` keeps its hit on the mail row; it reads subject and snippet, a weekday counts only after a day-setting word ("Would Thursday work?" is no date), and an all-day event counts on its own date. It compares against one live range read of each calendar per poll (yesterday to 61 days ahead). When a calendar read fails, the detector uses the calendars that the poll could read: a false hit is better than a hidden deadline. `event_soon` is its own signal.
  - **Classifier.** One utility call per 20 mail rows, at most 5 per poll, each row one try per poll. The mail is wrapped as untrusted, the answer is a `label_signals` tool call without a forced `tool_choice` (a 400 on current models), and each item is checked: an id of the batch and a label of the list. After 3 failures a row stays unlabeled and still shows. `SlotResult.modelCallId` links each label to its call. Text in one mail can steer the labels of its whole batch, and a quiet label without a hit closes a mail as `filtered`, so an injected mail can keep the other mails of its batch from the heartbeat; they stay on the Signals page with the call. One call per mail would limit this to the mail itself at about 20 times the calls; not done, an owner decision.
  - **Heartbeat.** It runs for signals also with an empty checklist. The digest (at most 20; detector hits first, then the `deadline` and `needs_reply` labels, then the newest; wrapped) carries one taint source per source and account. A completed run with a `heartbeat_respond` answer marks the shown signals `notified` when it sent a message and `seen` otherwise; a run that answered in text only did not decide, so it closes only the filtered signals and the next heartbeat shows the rest again. A message that did not reach the owner (the channel failed, so `owner.send` gave false) closes only the filtered signals too, adds no "sent this message" note to main, and its run is kept out of the recent notifications (setting `heartbeat_unsent_runs`, the last 5), so the next heartbeat does not take the signal for a repeat. The job still completes: a failed job backs off and is turned off after five failures, and a long channel outage must not turn off the heartbeat. The marks come after the send, so a crash repeats rather than loses a deadline. Quiet labels without a hit are `filtered` without a model call, and unhandled signals older than 3 days are `stale`. The model does not name signal ids. A gmail row that the detectors did not check yet waits while a poll run is open: the scheduler runs jobs at the same time, and a heartbeat in the gap closed a deadline mail without its hit. `npm run chat` runs the scheduler on the same database but does not poll: its scheduler leaves `poll` and `integration_poll` jobs out of its due list and its timer (`owns`, see 4.9), because its claim used up the slot of the background app, which then skipped that poll. Its heartbeat gets no signals, because it would tell the CLI and close them. It can still win the claim of a heartbeat; the signals then wait for the next heartbeat of the background app. (Replaced by 10.3: `npm run chat` runs no scheduler.)
- **The poll is a run.** The automation `{type: 'poll', source: 'google'}` runs a `runs` row (`sessionKey = poll:google`, `trigger = poll`), so its requests and its classifier calls show in one timeline with their cost, and the run's `error` holds its note. `scheduleContext` leaves poll automations out. The `polls` job map is generic, so Slack adds `slack`.
- **Risk of one call.** `Tool.riskFor(input)` and `Tool.accountOf(input)`. The caller computes the risk one time in the check and carries it in the gate; an approved call reads the risk and the account from the row of the call that asked, so `riskFor` never runs after the approval. A `riskFor` result of `external` asks the owner like `needsApproval`, so an allow rule on `calendar_create_event` never sends invitations. `tool_calls.account` is written.
- **Writes.** A send goes through a draft: after a lost answer, `drafts.get` decides: 404 sent; 200 after a 5xx answer not sent; 200 after no answer unknown, because Google can still be sending and the draft goes only when the send ends; else unknown. Recipients are lists of bare addresses, and a line break in a header field is refused. `calendar_create_event` takes attendees and derives its event id from the call, so a repeated approved call makes one event. Update and delete take `currentTitle` and check it before they act. A repeated delete counts as done.
- **Unsubscribe** takes `{account, messageId, sender, target}`, so the card shows both. At run time the tool reads the message again and checks the parsed From address against the sender exactly (a substring test let `"bank@x" <evil@y>` pass), and that the header offers the target. A one-click target needs `List-Unsubscribe-Post` and, in the top `Authentication-Results` header (authserv-id `mx.google.com`; a lower one can come from the sender), a `dkim=pass` for the From domain or a parent or child of it, whose one `DKIM-Signature` (matched by domain and `header.b`; when two fit, a forged one can copy both, so the pass counts for nothing) covers both unsubscribe headers (RFC 8058). From and both unsubscribe headers must each be there one time: a signature that names a header once signs its last instance, so a resent signed mail with an added header on top still passed; the POST uses `node:https` with a lookup that refuses private addresses inside the connect (DNS rebinding), no redirects, one 15 s deadline for the whole request (an idle timeout alone let a sender that sends one byte each second hold the call for hours), a result at the status line, and a 64 KB answer cap. A mailto target goes through the draft send, only with `send`, and it needs the same aligned DKIM pass, with `List-Unsubscribe` covered and there one time: a forged From with a mailto target made the owner's account send the forger's subject and body to a third party. The refusals do not quote the From address or its domain, because the output has no untrusted marker. A refusal has no `effect`, so it never gives the approval back to the owner.
- **One recorded fetch.** The OAuth client's `fetchImplementation` and the one-click POST write `google_requests` rows: before the request leaves (a failed row write stops the request, effect `none`), then the status, latency and answer (fail open). No header is stored; token, code, verifier and secret fields are removed by name before the redactor; an answer over 8 KB goes to a blob. An `AsyncLocalStorage` context links each row to the run and the call of a tool, or to the poll run, so a token refresh shows inside the call that needed it. A dedicated table, not `mcp_messages`: the rows are HTTP, not JSON-RPC.
- **Dashboard.** A Google page (status, what to do, Connect, the client upload, the last poll, the tools) and a Signals page (label and model call, detector hits, what happened with the message and the run). A Google tool call opens to its requests, and a poll run lists its requests.
- **Schema.** `010_google.sql`, and `011_google_calendar_page.sql` for the calendar position: `google_accounts` (with both cursors and `failures`), `google_requests`, `integration_events`. `src/db/index.test.ts` checks only the migration names before 008. `012_google_alert_claims.sql` and `013_signal_heartbeat_failures.sql` came with the verification rounds. (Built as 008 to 011; the merge renumbered them after Slack's 008 and the workshop's 009, `approvals.unsentAt`.)
- **Known gaps after M3.**
  - The first calendar read with `timeMin`, a calendar page token kept 15 minutes between polls, and the 7-day Testing-mode expiry are unverified against real Google; they are in the manual checks of the guide.
  - A cancelled event by someone else is often not recognized (no organizer in the delta).
  - After an outage longer than about a week, the resync looks back only 2 days.
  - A message that Google answers with a 5xx at every read fails each poll of its account (a 4xx is skipped).
  - That Google answers `unauthorized_client` for a refresh token of another client is from memory, not checked against real Google.
  - After a lost send answer, a draft that the owner deleted in that second reads as sent; the output says so.
  - The date heuristics (a shared word of 4 letters, US month/day) need tuning with real mail. Some honest one-click senders fail the DKIM gate; the owner gets the link.
  - **Taint through memory (2.5) is now live.** Mail read by main or the heartbeat can reach daily notes and `MEMORY.md`, and a heartbeat relay taints main until `/new`, so allow rules on external tools stop working there. The owner should rule on this before Slack and review merge.
  - The write tools ask the owner until the reviewer exists; the guide shows the allow rules.

### 4.8 Decisions from phase 2 M3, verification round 4

- **A Google alert is sent again until it reaches the owner.** `notifyOwner` gives the boolean of `owner.send`. The needs-auth claim (`alertedAt`) is still a compare-and-set before the send, but a failed send releases it, and every poll calls `accounts.alertPending()`, which also covers parked accounts (they are not polled). The stall message has its own claim, `google_accounts.stallAlertedAt` (migration 012): it fires at 12 or more failures, stays only after a delivered send, and clears when the count falls below 12.
- **A signal that fails the heartbeat loses its text.** A heartbeat run with status `failed` adds 1 to `integration_events.heartbeatFailures` (migration 013) of each shown signal; an aborted run does not. From 2, the digest shows the signal with its kind, label, account and detector names, but without its summary and the detector details (they quote the subject). So a text that every run refuses costs two failed runs, under the five that turn the heartbeat off. Two, not one, so one model or network failure keeps the text. Rejected: closing such signals (a model outage would then close real deadlines) and a new `handledAs` value (a table rebuild).
- **Account `all`** names each account that it did not check, with the reason.
- **`gmail_label` cannot add `TRASH` or `SPAM`** (schema refusal, before any approval). The guide lets the owner allow the tool also after reading mail, so text in a mail must not make it delete or hide mail.
- **Authentication-Results** are split by one scan that drops comments and the text of quoted strings (RFC 8601), so a quoted envelope sender cannot hold a forged `dkim=pass`.
- **A one-click counts as sent after the TLS handshake** (`secureConnect`, or at once for a reused connected socket), so a bad certificate gives effect `none`.
- **An aborted classifier call uses up no label try.** A failed call still counts, so a model that keeps failing is called at most three times per row; the cost of a long outage is unlabeled rows, which still show (fail open).
- **Code-made automations ask before a pause, a new schedule or a delete.** `automations_update` (with `enabled` or `schedule`) and `automations_delete` have a `riskFor` that is `external` for any payload other than `agent` and `system_event`, so they always ask the owner, tainted or not. This also covers the heartbeat, which had the same gap since phase 1. The dashboard still pauses without a card.

### 4.9 Decisions from the merge of phase 2 M3

- **One `integration_events` table for Slack and Google.** Slack's migration 008 and Google's migration both created it. Google's migration (now 010) builds it again with the columns of both and copies the Slack rows. `summary` and `untrustedSource` can be null (a mail row has only its id at first; a Google row has no `untrustedSource`, the digest names source and account). Slack's `occurredAt` became `occursAt`, which already meant the time of the item (a mail's arrival, an event's start); `slack-dms.ts` writes it.

Feeding DMs to the heartbeat needs its own choices (`dm_reply` rows, labels for DMs), so it waits for a decision; it is the next step for 4.2.
- **Two poll payloads, one `owns`.** `integration_poll` (Slack, keyed by integration id in `JobDeps.polls`) and `poll` (Google, keyed by source in `JobDeps.sourcePolls`) stay apart, so an integration entry named `google` cannot take the Google poll. Google's `skipTypes` became the workshop's `owns` predicate: `npm run chat` owns neither poll type nor the workshop. Before, chat claimed a due Slack poll and skipped it, which used up the slot of the service. (Replaced by 10.3: `npm run chat` runs no scheduler, and `owns` is removed.)

### 4.10 Decisions from phase 2 M3, verification after the merge

- **Only a failure that the text can cause counts against a signal.** A heartbeat run adds to `heartbeatFailures` only when it stopped at the step limit or its last model call was a refusal. A transient error, a rejected request or a crash does not count, so a model outage no longer strips the text of every open signal. Rejected: holding text back only on the last try before the heartbeat is turned off (it couples the digest to the scheduler's count).
- **Suspects get a run each.** A failed run still counts against all the signals that it showed, but the digest then shows at most one signal with 1 failure per run (the first in its order); the other suspects wait, neither shown nor closed. So a real deadline that sat next to a refused mail gets a run of its own and keeps its text; only the refused mail reaches 2 and is shown without text. Signals with 0 failures and held signals show as before.
- **A heartbeat that read outside text cannot change the checklist.** `heartbeat_respond` ignores `checklist` when the run's session has taint (a digest, or a checklist that a tainted session wrote), and says so in its result; `notify` and `text` still count. The main session keeps `heartbeat_checklist_set`, where the owner sees the change. Rejected: an approval for the field (the heartbeat session has no owner in it) and removing the field (a clean heartbeat could tidy its own checklist since phase 1).
- **The poll does not wait for its alerts.** The stall message and `alertPending()` start without `await`; the stall claim is released when its send ends without success. A send that hangs (Telegram waits up to 500 s per request) no longer keeps the poll run open, which hid every account's new mail from the digest.
- **Only the primary calendar counts.** The sync, the detectors, `calendar_list_events`, `calendar_freebusy` and the writes use each account's primary calendar. A deadline on another calendar of the account (a class calendar, a subscribed feed) gets a `date_not_on_calendar` hit, and the hit's detail says "the primary calendars", so the heartbeat does not claim more than it checked. Reading the calendar list was left for later: the calendars that the owner shows also include holidays and other people's calendars, and each of the detector, the event-soon signals and free/busy would need its own choice of which ones count.

### 4.11 Decisions from phase 2 M3, verification round 2 after the merge

- **More failures count against the shown signals** (this widens the first rule of 4.10). A heartbeat run counts when it stopped at the step limit, when any model call of the run was a refusal (also when the fallback model then failed), when the provider rejected the request (`ModelError('request')`, for example a 400 content filter; `RunResult.rejected` carries it), and when the run completed without `heartbeat_respond` (a plain answer or a reply cut at `max_tokens`). A transient error, an aborted run and a crash still do not count. The cost: a request bug in the app, or a model that often forgets `heartbeat_respond`, holds text back sooner; the signals still show with kind, label and detector names, so this is the safe side against a mail that turns the heartbeat off or hides a deadline until it goes stale.
- **Recent notifications carry the taint of their runs.** The "Recent notifications" block of the heartbeat input can repeat a mail, so the run gets the session taint of each heartbeat run that it lists, and the block is wrapped as untrusted when that taint is not empty. So a mail cannot reach the checklist one heartbeat later. The cost: for up to 5 notifications after a tainted one, a heartbeat cannot tidy its own checklist; the main session still can.
- **`alertPending()` never rejects.** It catches and logs its own errors, because its callers (the poll, `park`, `parkAll`) do not wait for it, and an unhandled rejection ends the process.

### 4.12 Decisions from phase 2 M3, verification round 3 after the merge

- **Only a request error that the input can cause counts** (this narrows 4.11). `rejected` is set for a request error with status 400, 413 or 422, or with no status (an error event inside a stream), and not when the text says credit balance, billing or quota. A bad key (401, 403), a retired model (404) and an empty credit balance are owner setup problems: they count like an outage, so they no longer hold back the text of real deadlines. A request error still skips the fallback model, as in phase 1.
- **The taint of a recent notification ends.** The heartbeat's `system_event` keeps `readTaint` (its checklist and digest taint) next to `taint`, and a later heartbeat takes only the `readTaint` of the runs that it lists (a run from before has only `taint`). Before, each run passed on the taint that it inherited, so one mail tainted every later heartbeat and every reminder relayed to main for ever. Now 4.11 holds: the taint lasts while the notification about the mail is among the last 5. The accepted cost: a tainted heartbeat that copies the mail's text into its own notification gives a clean-looking line to the heartbeats after the window; that text already reached the owner as a message.
- **The date detector skips a day before the day of the poll.** A poll can find mail days after it arrived (the computer was off). A passed day is not a deadline, and the live calendar read (from now minus one day) does not hold its events, so it gave a false "0 events that day" hit.
- **A mailto unsubscribe goes only to one address in the sender's domain.** The DKIM gate stops a forged From, but a sender that signs its own domain chose a percent-encoded third party, subject and body, and the card showed only escapes. The decoded recipient must be one plain address whose domain is aligned (relaxed) with the From domain; the sender's subject and body stay, because list servers read tokens there, and they now go only back to the sender. The cost: a list whose mailto address is at its mail provider's domain is refused; one-click or a manual unsubscribe still work.
- **The sign-in code and the PKCE verifier are secrets.** `exchange()` registers both before the token request, and the redactor also hides the form-encoded form of each secret (`~` is `%7E` there).
- **`all` is not an alias.** The read tools take `all` for every account.

### 4.13 Decisions from phase 2 M3, verification round 4 after the merge

- **A rejected heartbeat counts only when the same check without signals completes** (this replaces the status filter of 4.12 as the deciding test; the filter stays as a cheap first step). Setup errors are also a 400: a max_tokens or an effort that the model does not take, or a model without tools. No error text tells them from a content filter, and an allow list of input errors would let a mail that fails every run in a way not on the list stop the heartbeat for days. So after a rejected run that showed signals, the heartbeat runs once more with the same checklist, notifications, slot and tools, but without the signals and without `heartbeat_respond`. Only when that run completes do the signals count the failure. Tried and not taken: matching the error text (a new provider message breaks it), and counting only after an earlier run without signals succeeded (with open signals no such run happens). The cost: one more model call for each rejected heartbeat with signals, also while a setup error lasts.
- **An error event inside an Anthropic stream gets the status of its type** (`rate_limit_error` 429, `authentication_error` 401, `request_too_large` 413, and so on). Before, every type other than an overload or an api error was a request error with status 0: a rate limit was not retried, and it counted as an input error.
- **The recipient of a mailto unsubscribe is in the From domain or a child of it** (this narrows 4.12). The relaxed alignment of the DKIM check also let the recipient be a parent domain, which can be another organisation that gave the sender its subdomain. The cost: a list that sends from a subdomain and unsubscribes at its parent domain is refused; one-click or a manual unsubscribe still work.

### 4.14 Decisions from the final review of the phases

- **`/status` names each Google account** with the state of its sign-in (`google:<alias> ok`, `needs auth` or `signed out`), after the MCP integrations. Before, the owner could not see on the phone that Gmail and Calendar work; the alerts only say when they stop.
- **The one-click post of an unsubscribe has its account in the trace.** It runs outside `accounts.run`, so its `google_requests` row had no account and the counts of the Google page missed it.

## 5. Permissions, review, and sandboxing

### 5.1 Policy engine

Every tool call, built-in or integration, goes through `decide(call, ctx)`, which returns one of four decisions:

| Decision | Effect |
|---|---|
| `allow` | Runs now |
| `review` | A reviewer model checks the exact action first |
| `approve` | The owner must approve with a button (Phase 1 approvals) |
| `deny` | Does not run; the agent gets the reason |

The decision depends on:

1. **Static rules** in `okc.policy.json`: patterns on tool name and arguments, with allow or deny. A matching deny rule always wins, in any position; otherwise the last matching allow rule decides. Example: allow `google__gmail_archive` for senders in a newsletter list.
2. **Risk level**:
   - `read`: allow;
   - `write`: review;
   - `external`: approve.
3. **Taint.** If the run is tainted, `external` always needs approval, and `write` actions that carry run data outward go to review.
4. **Session profile.** A heartbeat or sub-agent can be stricter than the main session.

### 5.2 Reviewer model

The reviewer is a separate call on the `utility` slot. It sees:
- the exact tool call;
- the owner's last request in this run;
- a list of untrusted sources that entered the run;
- the policy reason.

It returns `allow` or `hold` with a reason. A hold does not run the tool. The agent gets the reason and can change course or ask the owner. Every review is a `model_calls` row linked from `policy_decisions`.

### 5.3 What the policy design takes

- **Default mode.** Risk levels and static rules decide. A reviewer model checks `write` calls, and the owner approves `external` calls.
- **What the reviewer catches.** Prompt injection and malicious actions; the action is held. The taint rule adds to it: an outbound action after untrusted input always needs the owner.
- **OS isolation.** Code runs in a Docker sandbox, and there is no host shell by default (on hold, see 5.4). Phase 5 M9 built it as a fresh container for each call (5.8).
- **MCP.** Lazy schemas through `tool_search` and `tool_call`, with a stable tool list for caching.
- **Large outputs.** Stored out of context, with a preview, a handle and `result_read`.
- **Sub-agents.** They inherit the permissions of the parent and cannot start sub-agents of their own. They also have explicit tool profiles and their own trace.
- **Owner in the loop.** Approvals by Telegram button for anything that leaves the machine; a hold goes back to the agent.

### 5.4 Sandbox for code and shell

On hold (section 10) until phase 5. Phase 5 M9 built the sandbox, and 5.8 records its decisions. The text below is the old plan; where it differs, 5.8 wins. In particular, M9 uses a fresh container for each call, not one long-lived container, and it does not offer the server-side code tool of a model provider.

**Decision:** one long-lived Docker container, `okc-sandbox`, through Docker Desktop (on Windows it runs through WSL2).

- **Container settings:**
  - non-root user;
  - `--cap-drop ALL` and `--security-opt no-new-privileges`;
  - memory, CPU, and process limits;
  - read-only root filesystem;
  - a Linux-side volume `okc-work` mounted at `/work`;
  - no host folders mounted.
- **Network** is off by default (`--network none`). A call can ask for network. That request goes to review, and the container then reaches the internet only through a host-side proxy with a domain allowlist.
- **Tools:**
  - `sandbox_exec { command, timeout?, network? }`: output through handles;
  - `sandbox_write_file` and `sandbox_read_file` (inside `/work` only);
  - `sandbox_put_file`, which copies a file the owner shares into `/work`.
- **For pure computation on Claude models**, the adapter can offer Anthropic's server-side code execution tool instead. It has no internet, runs on Anthropic's servers, and is free when web search is in the same request. It is a per-slot option, off by default.
- **No host shell by default.** A `host_exec` tool for PowerShell exists only behind a config switch, and every call needs approval.
- **Tradeoffs considered:**
  - A WSL2 distro would be faster but mounts the C: drive and runs Windows programs unless hardened.
  - Windows Sandbox is not available on Windows Home.
  - Anthropic's `sandbox-runtime` on native Windows is still alpha.
  - Remote sandboxes (E2B, Daytona, Modal) are strong but cost money and send data off the PC.
  - Docker is the best balance for one PC.

### 5.5 Decisions from phase 3 M3

This section covers the reviewer, the exfiltration guard, taint across sub-agents, and `delegate` (section 6).

- **Reviewer.** `src/policy/reviewer.ts` makes one call on the `utility` slot, recorded under the run of the checked call, so its cost counts in that run. The slot runner returns the `model_calls` id, and the decision stores it in `reviewerModelCallId`. The slot (`utility`), the time limit (60 s) and the input limit (24,000 characters) are constants, not config.
  - **Input.** One user message with four blocks:
    - `<owner_request>`: the last owner message of the session since its last reset. A `sub:` session reads the session of its parent (`subagent_runs.childRunId` → `parentRunId` → `runs.sessionKey`), never its own task, because the parent model wrote that task and an injection can steer it. A session without an owner message gives its first `system_event` as `<run_task>`, marked "no message from the owner" and wrapped, because a model can have written an automation prompt. A run that the owner did not start (an automation or a heartbeat, also in the main session) gives the first `system_event` of that run, not the last owner message of the session, which is older and is not its task; a child of such a run reads the same (verification round 2). A run with an owner message of its own reads that message, not the newest one: the owner can approve a delegate call after a later message, and the child does the task of the old run (verification round 3).
    - `<untrusted_sources>`: the source names only. The untrusted text never reaches the reviewer.
    - `<policy_reason>`.
    - `<tool_call name risk>`: `redactedJson(input)` with `<` and `>` as `<` and `>`, so an argument cannot close the block. The other blocks get HTML entities.
  - **Verdict.** One tool, `review_verdict {verdict: allow | hold, reason}`, checked by a strict zod schema, with `tool_choice` left at auto: Opus 5.5 and Sonnet 5.5 refuse a forced tool choice (DESIGN 8.3). A text verdict with a regular expression was rejected: the tool is stricter and costs the same.
  - **Failure goes to the owner.** No verdict, an invalid verdict, a call of another tool, two verdicts that disagree, a model error, a refusal through the whole chain, the 60 s limit, and an input over 24,000 characters (no model call is made) all throw. The caller contract (2.5, rule 3) then asks the owner. A cut input was rejected: padding can hide the recipient.
  - **Hold text.** The model reads the reason and the way out: "Change course, or ask the owner. The reviewer reads the owner's last message, so if the owner confirms this exact action, you can try it again." A sub-agent reads "Return to the parent agent and say which call it held."
  - **Measurement.** The tests prove the wiring with a fake reviewer. `npm run smoke:reviewer` (`src/smoke-reviewer.ts`, manual, about 30 calls of the utility slot) sends 10 injected actions, 10 normal actions after an untrusted read, and 10 urls to the real model and prints the hold and allow counts. If the hold rate is low, raise the effort of the `utility` slot, then change the model.
- **Exfiltration guard.** A branch of `decide()`, only in a tainted session: after the deny rules, `needsApproval` and the tainted-external rule, and before the allow rules, because an allow rule cannot see the data in a call. Decision `review`, rule `exfiltration`; the reason names the url (cut to 200 characters) and the signal.
  - **What counts.** Every url in every string of every tool input, after NFKC, so it covers the tools of the other milestones and the MCP tools without a field list: a query or a fragment of any length, a host and path over 48 characters, or a host label over 32 characters (a dns lookup leaves the PC too). A length limit on the query was rejected: 24 bytes of a secret in base64 fit in 31 characters. The path limit was 100 until verification round 2, which sent 57 bytes in a path and 48 bytes in two labels with no review; 48 keeps common links that a model writes (`en.wikipedia.org/wiki/Albert_Einstein` is 37) and sends a longer one to the reviewer, unless it was read. An encoded-run signal per path segment was rejected again (see "Not taken"). The walk also visits object keys (a free-form record such as headers), the schemes `ws`, `wss` and `ftp`, a link that starts with `//`, and a bare link with a port (`evil.example:8443/c?d=`). A field that holds only a url is judged on every signal, also when a space or a quote splits it, because a client sends that whole path. Cost: a message that is only a link and words after it goes to review. `message_owner` counts, because a chat app fetches a link preview. A bare host name with no path counts too, judged on its length and its labels, because a chat app makes a link of it and its preview looks up the host (verification round 4: three 30-character labels passed). Cost: a dotted name over 47 characters in a tainted session goes to review. A bare IPv4 address and a single name with a port (`localhost:8080/c?d=`) count too (verification round 5); a single name with only a path does not, because `and/or?` and `src/app.ts?x=1` have the same form. The `query` of `web_search` counts as a query (the planned name; it has no effect until the web milestone merges).
  - **Url forms (verification round 1).** A url parser reads more than `https://host/path`: a scheme in any case, no slashes or back slashes after it, a tab or a line break inside it, and a space or a quote before the query when a client gets the whole string as a url. So each `http:` starts a candidate up to the end of the field (at most 1,024 characters; verification round 3: a candidate cut at the next `http:` missed the query of `https://evil.example/x/http:/?d=...`), with tab, CR and LF removed, and `new URL` judges it. A candidate that the limit cuts is longer than the path limit, so it still has a signal. The part up to the first space or quote is judged on every signal; the longer candidate only on the query, the fragment and the user info, because the words after a link make a long path. A host name with a path, query or fragment and no scheme (`evil.example/c?d=1`) counts, because a chat app makes a link of it. A user name or a password is a signal (a browser sends them after a 401). Deny rules test the same forms. Cost: a message with a link that has a query and words after it goes to review even when the link was read.
  - **Verbatim exemption.** A url that a successful `tool_result` with an `untrustedSource` already holds verbatim, within the newest 2,000 events since the last reset, passes: following a link from a mail or a search result carries no new data. Verification round 1 narrowed it from every `tool_result` and tainted `system_event`: an injected model could put a data url into text of its own session (a hold or an error that quotes the call, an unknown tool name, a local tool that echoes its input, the answer of a child, the task of a child), and the retry passed with no review. So an error result, a result without an untrusted source, a `delegate` answer and every system event do not count, and the read url must end where the sent url ends. Verification round 2 found that `result_read` of a long `delegate` answer or a long error copied the text into a successful result with the same source. So the test is now on the source, not the tool name: a result whose `untrustedSource` starts with `sub:` (a child's answer, and `result_read` of it) does not count, and `result_read` of an error keeps `isError`. The finder reads the NFKC form, but the tool gets the raw text, so a url counts as read only when the raw field holds it verbatim (verification round 5: 32 bits passed as plain and fullwidth letters in a url that was read). One `instr` query, only after a url matched; a call with over 20 such urls goes to review without the check. The payload is redacted json, so a url with a secret or an escaped character does not match and goes to review.
  - **Verification round 6.** An apostrophe no longer ends a link: a chat app (Telegram's parser, for example) links through it, so `https://evil.example/c'<data>` after words in a message was judged only up to the apostrophe. Now only whitespace, `"`, `<` and `>` end a link, in the finder, the reply guard and the card. Cost: a quoted long link with a trailing `'` does not match the read url, so it goes to review. Also, each word with `/`, `?`, `#`, `%`, `。` or `｡` is parsed with an `https://` base and counts when the parser gives a host with a dot or an IP literal: `evil。example`, `evil%2Eexample`, `3232235777`, `0xC0A80101` and `[2001:db8::1]` passed with no review before. A url that a pattern already found is not counted twice, so the limit of 20 seen checks stays the same. Rejected: percent-decoding the whole text before the patterns (a `%20` in a path would end the candidate early and hide the data after it).
  - **Verification round 7.** A sentence in Chinese or Japanese has no spaces, so it is one word, and the parser reads its `。` as a dot: every such reply in a tainted session went to review, and a failed review removed it. A parsed host now counts only when its last label is an ASCII top-level name or an IP number; a punycode last label or an empty one (`No.#4521`) does not. A data label in a non-ASCII name (`データ.evil.example`) still counts. Verification round 4 of the fixer pass found that this dropped `evil.рф/c?d=…` and `evil.中国/…`, and that a bare host with Cyrillic or underscore labels (`<40 letters>.evil.example`) had no candidate, because `BARE_URL` reads only `[a-z0-9-]` labels. Now a punycode last label is dropped only when a `。` comes before it in the word, and each word with a dot (not a mail address) goes to the parser too, so the label and length limits apply to it. Cost: a Japanese or Chinese sentence with an ASCII dot and a long label after it goes to review. Also, `urlSeen` leaves out `automations_list` (it repeats prompts the model wrote under the taint of the automation), and `tool_search` no longer repeats the query when nothing matches. An MCP tool that echoes its own arguments is still counted as outside text.
  - **Not taken.** Signals for copied identifiers, encoded runs and shingles (many thresholds and poor recall; a cheap reviewer makes "any query" affordable), an opt-in `Tool.egress` field (no tool declares it, and MCP tools are left out), an exemption for the owner's own text (it lets the owner's private data out in a short query), and a deny on a signal.
- **Final reply guard (verification round 4).** The final reply of a run goes to the owner's chat with no tool call, and a chat app fetches its link preview. So `agent()` in `app.ts` passes the text of each completed run through `guardReply` (`src/policy/reply.ts`) before the router or the automation runner sends it. In a tainted session, a link with a signal that the session did not read goes to the reviewer as the pseudo tool `reply_to_owner` (risk `write`). An `allow` sends the reply as it is. A hold, a reviewer failure or no reviewer replaces each such link in the chat text with "[link removed: …]"; a link that the text does not hold verbatim (an NFKC form) replaces the whole reply. The event log keeps the full reply for the run page. Rejected: link previews off per channel (each channel needs its own option, the CLI has none, and the link stays one tap away), and removal without a reviewer (a link that the owner asked for, for example a map search, would always go).
  - **Verification round 5.** The guard runs inside `runAgent` (the `guardReply` hook of `RunInput`, which only `agent()` sets) before `finish('completed')`. A crash during the review (up to 60 s) then leaves a `running` run that the sweep closes, not a completed run whose reply never came. Each review writes a `policy_decisions` row (`toolCallId = 'reply'`, tool `reply_to_owner`, rule `exfiltration`, with the verdict and the reviewer call). A removal also appends a `note` without the links ("The final reply did not go to the owner's chat as it is: …"), so the next run knows that the owner did not see them. The run page shows the decision as a `reply_to_owner` item after the turns, with the reviewer call inside it, and outcome `held`, `ran`, `running` (review in progress) or `interrupted` (the app stopped during the review).
  - **Verification round 6.** A crash during the review left the model with its undelivered reply and no note, and the owner was never told. Now `repairSession`, at the start of each run, looks at the newest `reply` decision of the session; with no verdict and no reply note, it appends the note "… the app stopped while the reviewer checked it, so the chat did not get it." under the stale run, so the model and the run page know. The sweep that closes such a run sends the owner one message without the link. A reviewer failure now writes "the reviewer failed (…)" into the reason, says "the review failed" in the note, and links the paid model call (`ReviewError.modelCallId`), so the run page shows it inside the item; the tool path links that call too. Remaining: as for tool calls, a second process that runs the same session during a slow review can add the note too early.
- **Approval cards in a tainted session (verification round 5).** A card goes to the chat before the owner decides, and a chat app fetches a link preview of it. A tainted `external` call goes to the owner by the taint rule with no review, and a failed exfiltration review sends its call to the owner with the url in the field line and in the "Why:" line. So in a tainted session `cardText` writes each link with a signal with `[.]` and `[:]` (`https[:]//evil[.]example/c?d=…`) and adds one line that says so and points to the dashboard; a line with a link that it does not hold verbatim (an NFKC form) gets the marks in the whole line. An untainted card stays as it is. Rejected: `link_preview_options` per channel only (the same reasons as for the reply, and the owner can still tap the link), and dropping the link from the card (the owner must see what the call sends). Remaining: the reply to `/approve` and a late result can quote the tool output, which can echo the url; by then the owner approved the call.
- **A sub-agent never asks the owner.** No run reads the result of an approval in a `sub:` session, and the owner did not start the child. So `decide()` turns an `approve` in a `sub:` session into `deny` with rule `subagent` and a reason that tells the child to report the call to its parent, and a review without a usable reviewer becomes a recorded hold (`reviewerVerdict = hold`). No approval row is ever made for a child. The parent can make the same call and gets a normal card. A relay of a child's approval to its parent was rejected: it is a second writer into another session's queue in the approval flow, and it still drops late results and sweep notes of the child.
- **Taint across sub-agents** uses the paths of 2.6, with no new mechanism. Down: the first event of the child is `system_event {text: "Your task from the parent agent: …", taint: sessionTaint(parent)}`, so the child starts as tainted as its parent and the provenance names the parent call that read the source. A delegate call that the owner approved (`approval-N`) uses the taint snapshot of its decision instead, as the approval note does, because the owner can send /new before the approval (verification round 4 of the fixer pass: the child started clean and its data link passed with no review). The task is not wrapped: it is the instruction of the child, and the policy guards each call of the child. Up: when the child session is tainted, the output of `delegate` has `untrustedSource = "sub:<profile>:<childRunId> (<sources>)"`, so the caller wraps it and the parent session is tainted with a source that names the child run. The list names only the sources that the child read itself; with none, the source is the child key alone. Verification round 4 found that a list with the inherited sources doubled the newest source with each delegate call (1 MB after 16 calls). A reason, an approval card and `<untrusted_sources>` name at most 5 sources, each cut to 200 characters, with "and N more"; the decision keeps the full list. A taint array on `ToolOutput` was rejected: it changes shared payload shapes for provenance that the child run already holds.
- **Taint names.** `sessionTaint` takes the name of a `tool_call` result from its trace row, so a card says "read by mail__read_inbox", not "read by tool_call". The event alone decides the taint. The lookup runs one time for each source after deduplication, so a session with 50,000 events still checks in well under 1 ms.
- **`delegate`** (`src/agent/delegate.ts`): `{profile: browser | research | inbox, task ≤ 8,000}`, risk `read`, in the main and automation tool lists, with the built-in allow rule "delegate starts a sub-agent; each call of the sub-agent gets its own policy decision".
  - **Profiles are code**: browser (slot `main`, 30 model calls), research (`main`, 20), inbox (`batch`, 40). There is no `code` profile while the sandbox is on hold (phase 5 M9 adds none either, see 5.8). A planned tool name that the app does not have is left out; the description lists the live tools of each profile, computed at start, so the `tools` parameter is stable. An integration reaches a child only through `"sessions": ["sub:<profile>"]` in `okc.integrations.json`. A test lists the planned names that this build does not have (the browser, web and gmail tools); the merge must make that list empty.
  - **Depth 1.** No profile lists `delegate`, and the tool refuses in a `sub:` session.
  - **At most 3 children per parent run**, counted in memory. A fourth call gets an error at once ("wait for a result, then try again"); a wait would hold the parent turn with no result.
  - **No budget input and no timeout per child.** The iteration limit of the profile bounds a child, and it runs under the tool signal of its parent and its own background run timeout.
  - **The child run.** The `subagent_runs` row comes first; then the child runs in `sub:<profile>:<childRunId>` through the session queue, with trigger `subagent`, the slot and limit of the profile (`RunInput.maxIterations`), the base instructions and `SUBAGENT_INSTRUCTIONS`, and no persona files, no `USER.md`, no goals and no automations in its context. It does not go through the app's `agent()`, so the owner gets no "did not finish" message; the parent reports instead. The key ends with the run id, so the stale sweep of 2.5 repairs a crashed child.
  - **Result.** A completed child gives its final text (the preview-and-handle rule applies). An empty text or `NO_REPLY`, which the base instructions allow in every session, gives "The <profile> sub-agent gave no answer." (verification round 4). A stopped or failed child gives `isError`, the reason, its last text, and each of its tool calls with its outcome word (`outcomeOf`), so the parent does not repeat an action that ran.
- **`subagent_runs`** (migration 016, built as 008): `id, parentRunId, toolCallId, childRunId (unique, no foreign key, because the row comes before the child run), profile, createdAt`. This differs from 2.2: `task`, `resultSummary` and `endedAt` are left out, because they are copies of the input and output of the `delegate` row (joined by `parentRunId, toolCallId`) and of the child's `runs.endedAt`. `toolCallId` is new, because a run can delegate several times.
- **Dashboard.** `getRunDetail` gives a `delegate` call its `child` (profile, status, cost) and a child run its `parent`. While the child runs, the `delegate` row does not exist yet, so the call shows with outcome `running` and its child, from the `subagent_runs` row and the turn that asked for it. When the parent run or the child is closed (a crash, then the stale sweep), the same placeholder shows as `interrupted` with "The app stopped while the sub-agent ran", because the row comes only at the next run of the session (verification round 2). A delegate call that the owner approved runs as `approval-N` after its run ended, and no turn asked for it under that id, so it shows as a call of its own after the turns, with the input of the approval; only the status of its child tells if it still runs (verification round 3). A model call that is the `reviewerModelCallId` of a decision leaves the turns and goes into the policy view of its tool call (`reviewerCall`); a placeholder finds its decision by run and call id, so a reviewed delegate call shows its review while the child runs (verification round 4). A reviewer call with no verdict (an error, a retry, an unclear answer) has no such link; it is found by `review_verdict` in its tool catalog and listed with the turn whose tool calls it checked (`reviews`), because the tool calls of one turn run at the same time and the row does not say which one it checked. The run page renders the child timeline inside the delegate call with the same `Timeline` component, a child page says "Started by call … of run …, as the inbox sub-agent", the header adds "+$x in N sub-agent runs", and the runs filter has `subagent`. A running run page also loads again on the stream message of each new `subagent` run, because a page that loaded during the review of a delegate call has no child to follow and the parent writes no event until the child ends (verification round 4 of the fixer pass).
- **Known gaps after M3.**
  - **Live change.** A `review` decision that went to the owner now goes to the reviewer: on master only integration `write` tools without an allow rule; after the merges also Gmail label, archive and mark-read, browser typing and clicking, and Slack writes. There is no off switch; a reviewer failure still goes to the owner.
  - The judgement of the reviewer is not measured until the owner runs `npm run smoke:reviewer`.
  - The guard misses a short path: up to about 40 characters of data (about 30 bytes in base64) in the host and path of a short domain pass with no review. It also misses other schemes (`ssh:`, `git:`), data split over many calls, data in a free-text field without a url (left to the tainted-external rule), and the choice among links that an attacker supplied (the verbatim exemption). A url deep inside a long result behind a handle is not in the payload, so it is reviewed: a false positive only.
  - A tainted research or browser child reviews every search and every built query after its first untrusted read, at about 1 s and $0.0002 each. Measure after the web merge.
  - A child cannot get the owner's approval. An inbox child archives only with a reviewer `allow` or an allow rule.
  - Taint through memory (2.5) and the taint line in the `context` event (section 9) stay open.
  - `delegate` joins the main and automation tool lists, so the cached prefix changes one time at deploy.
  - A crash between the end of a child and the row of the parent's `delegate` call repairs that call as `interrupted`, although the child finished. The window is microseconds.

### 5.8 Decisions from phase 5 M9

M9 builds the code sandbox that 5.4 planned and section 10 put on hold. The tool is `sandbox_exec {language: bash | python | node, code, files?, collect?, timeoutMs?, memoryMb?, cpus?, network?}` (`src/sandbox/input.ts`). The contract is in `docs/PHASE5-API.md` (M9), and the owner's guide is `docs/setup/sandbox.md`. This section wins where 5.4 differs.

- **(a) A fresh container for each call.** 5.4 planned one long-lived container. M9 creates a container for each call and removes it after the call. The reasons:
  - no state leaks from one call to the next, except the files in the `/work` volume of the task;
  - a process that a call starts in the background ends with its container;
  - a crash of the app leaves no container that runs. The command runs under `timeout -s KILL` with its wall time and 5 s more, so a container that no process watches ends by itself. The start sweep removes each labelled container of this instance that has no running row, and the same sweep runs once more 6 minutes after the start, for the rows that a stopped process left young (an `okc restart` during a call). The stop of the app aborts the execs that run and waits until the runner has removed their containers.

  The cost is the start time of a container for each call, which is small next to a model turn.
- **(b) The engine API over its socket, not the `docker` command.** `src/sandbox/docker.ts` is a small client over `node:http` (API v1.44, Docker 25 and later). The reasons:
  - the app needs no `docker` program, only a socket. When the app runs in its own container (M7), it gets a socket or a socket proxy, and no CLI in its image;
  - each error has an HTTP status and a message, not text that the app must parse;
  - the attach stream is split into stdout and stderr in the app, so the output limit and the drain of the stream are exact;
  - the kill at the wall time is exact: the app kills the container by its id when the timer ends;
  - there is no shell quoting: the code goes to the interpreter as one argv entry (`bash -c`, `python3 -c`, `node -e`);
  - files go in and out as tar archives through the API, with no bind mount of a host folder. This also works when the app runs in a container and the engine runs on its host;
  - it adds no dependency.

  The cost: the app keeps the client, and it does not read Docker contexts. It reads `DOCKER_HOST` (`unix://`, `npipe://`, or `tcp://` without TLS; a `tcp://` address on another host gets a warning in the log, because the code and the files travel unencrypted) and the default sockets only (`~/.docker/run/docker.sock` on macOS, `/var/run/docker.sock`, on Linux `~/.docker/desktop/docker.sock` and the rootless `$XDG_RUNTIME_DIR/docker.sock`, and the pipe `//./pipe/docker_engine` on Windows).

  Every engine call of an exec, apart from the wait for the exit, has a limit of 30 s, and the whole exec ends after its wall time and 2 minutes. The volume, network and sweep calls have limits too, and the start sweep ends after 30 s. So an engine that accepts the socket and then hangs (Docker Desktop paused or updating) never holds a call, a run slot or the start of the app. The wait goes out before the start, and the runner starts the container only after the engine has sent the headers of the wait answer, which it does once the waiter is registered, so a short command cannot exit before the wait.
- **(c) The security settings of each container** (`ContainerSpec` in `src/sandbox/types.ts`, values in `src/sandbox/limits.ts`):
  - the user `1000:1000`, never root;
  - `CapDrop: ['ALL']` and `no-new-privileges`, not privileged;
  - a read-only root filesystem, and a tmpfs at `/tmp` (`rw,noexec,nosuid,nodev,size=64m`);
  - 128 processes, 512 MB of memory with no swap (`MemorySwap` equals `Memory`), and 1 CPU. A call can ask for up to 2,048 MB (`memoryMb`) and 2 CPUs (`cpus`);
  - the `fsize` limit of 256 MB, so no single file can grow over the size of `/work`;
  - `Init: true`, so a child process that the code leaves behind is reaped;
  - a wall time of 60 s, up to 300 s on request; at the end the container is killed. The command also runs under `timeout -s KILL` (see a);
  - at most 1 MB is kept for each of stdout and stderr. The bytes after the cut are counted (`stdoutBytes`, `stderrBytes`) and the result says that it is cut;
  - no network (`NetworkDisabled`, network mode `none`), unless the call has `network.allow` (g).

  The image (`sandbox/Dockerfile`) is pinned by the digest of its base and has no setuid or setgid file. The Debian packages are not pinned to versions, so the image is reproducible only up to the state of the Debian archive; each exec keeps the image id that ran it. The base sets the entrypoint `docker-entrypoint.sh`, and the create request of the code and the relay resets it (`Entrypoint: [""]`), so the command runs with no script before it. A new image definition gets a new tag (`okc-sandbox:2`), so an app never runs an old image under a new name.
- **(d) A scratch volume for each task.** A task is one segment of a session, from a `session_reset` to the next one. Its id is a hash of the session key and the id of the last `session_reset` (0 before the first), so `/new` gives a fresh `/work`. The calls of a task share one Docker volume at `/work`, so a call can use the files of an earlier call. `sandbox_scratch` keeps each volume. The start sweep and each call remove a volume that no call used for 24 hours, and a labelled volume of this instance without a row. While the command runs, the runner measures `/work` every 5 s, and it kills a command that wrote more than 256 MB (status `killed`, "the command wrote more than 256 MB to /work"). After each call the runner measures `/work` again; a volume over 256 MB is removed, and the result tells the model that `/work` is empty again. The `fsize` limit (c) keeps one file below 256 MB, so between two measures a call can write at most a few seconds of data over the limit. The row of a task is written before its volume is made, and the sweep reads the rows after it lists the volumes and again before each removal, so a sweep that runs during a call never removes the new volume of that call. A volume that cannot be removed does not stop the sweep of the others.
- **(e) Files through the blob store.** A file in is the text of the call or the blob of an earlier result. A text file (valid UTF-8 with no NUL byte) goes to the text store, which redacts it like every other text of the trace; any other file goes to the byte store as it is. After the end, only the paths in `collect` come back, each as a blob with its size and type. Each file in and out has a `sandbox_files` row. The limits are 20 files, 10 MB for each file and 20 MB for each call, in each direction. A name between two slashes has at most 255 bytes, as on Linux; a path that does not fit the ustar name and prefix fields goes into the archive with a pax record. An input blob must be one that a `sandbox_files` row names (an output of any exec, or a file of an exec of the same session), so a call cannot pull a screenshot, an attachment or a payload of another session into the container. The result of a call that reads an output of a call with network access has an `untrustedSource`. The redaction changes the data on reuse: a collected text file with a value that looks like a key comes back as a blob of the masked text, and a later call that passes that blob in gets the masked text. The tool description says so, and says to keep exact bytes in `/work`. `GET /api/sandbox/files/:hash` serves the bytes of a file that a row names, with the type of the row; a type other than a raster image downloads.
- **(f) Policy.** The new risk `exec` goes to the reviewer (rule `risk:exec`), as `write` does, because the code runs in an isolated container with no network. A call with `network.allow` is `external` through `riskFor`, so the owner approves each one, and the taint rule of 5.1 applies to it. The result has an `untrustedSource` only for a call with network access: without network, the output comes from the code and the files of the call, and the session holds both already. With network access, the output can hold text from outside, so it is wrapped and taints the session.
- **(g) Network through the egress proxy.** A call with `network.allow` (at most 10 host names; an entry also allows its subdomains) runs on a Docker network that reaches only the egress proxy of the app (`src/browser/proxy.ts`), with the proxy variables set. The proxy lets through only the hosts of the list, and the egress check refuses private addresses, as for the browser. `checkAllowlist` refuses a public suffix (`tooBroad` of `src/browser/gate.ts`) or a name that is not a host. The plan of each call (`NetworkPlan`) gives the hosts that the proxy let through and the requests that it refused, for the result and the trace (the `egress` column, `SandboxExecDetail.egress`), and the gate removes the network after the call. An entry is made a site in the same way as the host of a request (`siteOf` drops a leading `www.`), so the entry `www.python.org` lets `www.python.org` through. When the Docker host cannot give this route, `NetworkGate.check()` gives the reason in `SandboxStatus.networkReason`, a call with `network.allow` fails with that reason, and a call without it still runs. The route (`src/sandbox/network.ts`):
  - each call gets its own internal Docker network, which has no route out of the host, and its own proxy in the app with the allowlist of the call (`allowHost`). The proxy checks each address as the browser proxy does, so a name that resolves to a private address does not get through;
  - an internal network cannot reach the app, so a second small container, the relay (`sandbox/relay.mjs`, in the same image at `/opt/okc/relay.mjs`), sits on the internal network and on the default bridge. It pipes each connection to the proxy of the call and to no other address. The code container gets the relay as `HTTP_PROXY` and `HTTPS_PROXY` (and `NODE_USE_ENV_PROXY=1`, so the fetch of Node uses it). A direct connection, a UDP packet or a DNS query to an outside server finds no route. The relay has the same hardening as the code container, with 64 MB and 32 processes;
  - the relay tells the app that it listens with a tunnel request for a random name under `.okc.invalid`, which the proxy catches and does not count as a refusal. The call starts the code only after this signal (15 s limit);
  - Docker Desktop (macOS, Windows): the proxy listens on `127.0.0.1`, and the relay reaches it at `host.docker.internal`, which Docker Desktop forwards to the loopback address of the host (this forward to a proxy that listens only on loopback must be confirmed on a real Docker Desktop; only a fake engine checks it, and the integration test with a real engine does not run a call with network access yet);
  - the Linux engine: the proxy listens on the IPv4 address of the `docker0` bridge, never on `0.0.0.0`, and the relay connects to that same address, so the bind and the target can never differ. Other containers on the default bridge, and local processes on Docker Desktop, can reach the proxy of a running call on its random port, and the relay listens on all the addresses of its container. So each call has a random credential: the proxy answers 407 to a request without `Proxy-Authorization` for `okc:<token>`, and the code container gets it in its proxy variables (`http://okc:<token>@<relay>:3128`). The relay pipes raw bytes, so the credential passes through it unchanged, and the proxy drops the header before a plain request goes on. Only the ready request of the relay needs no credential; its name is random and the proxy always refuses it;
  - not supported: the app in a container (M7), because a sandbox container cannot reach a proxy inside the app container. `check()` gives this reason. `check()` also refuses an engine older than Docker 26, because an older engine forwards the DNS of an internal network to the outside resolver, which would let a call send data out in DNS names (this version boundary must be confirmed on a real engine);
  - after the call the gate stops the proxy, then removes the relay and the network. The start sweep removes the relay containers of a stopped process with the other labelled containers, and then its networks (`sweepNetworks`), also the probe networks of `check()` that are older than a minute (a younger one can be the probe of the other process of the instance);
  - `check()` keeps a yes, and a reason that cannot change while the process runs (the host, an old engine), for the life of the process. An engine that does not answer, or a probe network that could not be made, is asked again at the next check.
- **(h) Model-neutral (D16).** The sandbox runs on the owner's Docker for every model provider. The 5.4 bullet that offers the server-side code tool of a model provider per slot is rejected under D16: a core ability must not depend on one provider, and that tool would also put the code and its data outside the trace of 2.2.
- **(i) The tool is off without Docker or the image.** At the start, the app probes the engine (`/version`, 3 s limit) and looks for the image. An engine that runs Windows containers gets its own reason. With no socket, no answer or no image, the tool is not in any tool list, the status gives the reason, and the rest of the app runs. `toolsFor` is fixed at the start, so the `tools` parameter of a session stays stable for caching; a restart is needed after Docker comes up or the image is built. When the last probe says that Docker does not answer (Docker stopped while the app ran), a call returns an error with effect none. The dashboard status probes again when its last answer is older than 30 s. The tool is in the main session and in automation runs. There is no `code` sub-agent profile (section 6).
- **(j) The constants live in `src/sandbox/limits.ts`, not in config**, as for the reviewer (5.5). A wrong value only makes the sandbox weaker or less useful, and the tests check these values.
- **(k) The trace.** Migration 020 makes `sandbox_execs` again (004 made it and 006 dropped it), and adds `sandbox_files` and `sandbox_scratch`. A row links to its tool call by `runId` and `toolCallId`; the dashboard joins it to the `tool_calls` row and to its `policy_decisions` row (the decision, the reviewer verdict and the approval). Each row keeps the language, the code, the image and the image id that ran, the container id, the network mode and the allowlist, the limits, the status, the exit code, the stdout and stderr blobs with their full byte counts, the error and the duration. The tool writes the row with status `running` before the container is created, so a crash leaves a row; the start sweep, and its second pass 6 minutes later (a), close a running row older than the longest call and a margin (6 minutes) that this process does not run. A call that passed its checks and then fails before Docker runs it (the network or the container cannot be made) gets a row with status `error`. A call that the tool refuses before the row (Docker off, busy, a bad allowlist, path or blob, a scratch volume that cannot be made) appears only in `tool_calls`. The code in the row is redacted like every other text of the trace, while the container gets it as the model sent it. The row also keeps the egress of a call with network access and the collect paths that did not come back (`notCollected`). The waterfall (M1) shows each exec as a `sandbox` span.

### 7.1 Decisions from phase 2 M4

- **API shape.** The field is `rich_message: { markdown }`. grammY's typed methods (`sendRichMessage`, `sendMessageDraft`) replace `bot.api.raw`. Only a 400 falls back, per part: rich, then HTML parts, then plain text. Any other error goes up, because the Bot API has no idempotency key and a retry can show a reply twice. A part that went out is never sent again. A reply over 30,000 characters is cut first by a line scanner that knows code fences (it closes a cut fence and opens it again, and never cuts a surrogate pair).
- **Sanitizer before every rich send** (`telegram-safe.ts`). Rich Markdown renders raw HTML, so model text could carry a `tg-button` with the data of a real approval, a media tag, an image that Telegram fetches, or a `tg://` link that shows media. A raw-text pass with no parser puts a zero-width space after the `<` of each tag that is not on an allow-list (`b strong i em u ins s strike del code pre sub sup br p blockquote aside cite details summary tg-spoiler`), after the `<` of `<!` and `<?`, after the `!` of `![`, and after `tg` or `attach` before a colon. Markdown decodes references and escapes in a link destination, so a letter of the scheme can also be a numeric reference (`&#116;g`) and the colon can be `\:` or an entity (`&colon;`, `&#58;`). The owner sees the same text. The pass also changes code blocks: a first version kept a closed code fence as it was, and the first verification round found five inputs where the scanner and a markdown parser ended a fence at different lines (an indented fence, a no-break space or a CR after a closing fence, a no-break-space line in an HTML block, a fence in a list item), so a live tag passed as code. Only a full parser knows where a fence ends. The cost is a zero-width space in copied code that holds a tag, an image or a `tg:` scheme. Each send logs one `telegram send` line with the run id, the formats, the fallback reasons and the neutralized items; a non-empty list also logs a warning.
- **Signed buttons in the adapter** (`telegram-buttons.ts`). Each `callback_data` becomes `<data>.<mark>`, where the mark is 16 base64url characters of an HMAC with a key from the bot token. A press without a valid mark never reaches the router, and the owner sees "That button is not from one of my cards". Data over 47 bytes is a bug and throws. No table and no migration; a new bot token makes the old buttons invalid. The answer to a press is not awaited and a failure is logged: Telegram refuses the answer to a press that waited during a restart, and that must not lose the press.
- **HTML fallback.** The `marked` lexer (one new dependency, `marked@18.0.14`, with no dependencies) replaces an mdast walker. It reads parts of at most 2,000 characters from the line scanner, each in a `try`; a part that it cannot read goes out as escaped text. An image becomes a link, and a link keeps only an `http`, `https` or `mailto` scheme.
- **Streaming.** A model call streams only when the run gives `onText`; the body is the `create` body plus `stream: true`. An error event inside a stream with the type `overloaded_error` or `api_error` is transient. The slot runner gives `onText('')` before each attempt, so text of a refused or failed call leaves the draft. Drafts are plain text, because half-written markdown is often invalid. One draft is in flight at a time; a 1 s ticker sends a changed draft, and sends it again after 20 s of quiet. A draft over 4,096 characters shows `…` and the end. While tools run, the draft shows `⏳ <tool>` under the text (`RunInput.onActivity`; a `tool_call` shows the integration tool). After 3 failed drafts in a row a reply shows no more drafts; typing goes on every 4 s. The end of a reply waits at most 2 s for a draft in flight. A draft id is a random 31-bit number, kept only in memory. A stream that fails or that the owner stops gives its last snapshot with the error, and the slot runner writes it as the row's response with its usage and cost, because the owner saw that text in the draft.
- **Stop.** The stop button of a draft and `/stop` abort the main run before the session queue. A stop while a tool runs says "Stopped while X ran. Its effect is unknown." The session gets a `system_event` that the owner stopped the reply. `/stop` matches in any case, as the other commands do. `/stop` cannot stop approved calls, heartbeats or automations; while one of them holds the main queue, `/stop` and `/status` say so instead of "Nothing runs now."
- **Reactions.** 👀 at the start and 👌 when the reply went out (✅ is not an allowed bot reaction). A failed or stopped run, or a reply that could not be sent, clears the reaction. The end reaction goes out after the reply and nothing waits for it, so a hung reaction call never holds the reply, the next message or the stop of the app. It is chained after the start reaction, because Telegram applies requests in the order they arrive and a slow 👀 could otherwise replace 👌.
- **Link previews.** Every `sendMessage` (HTML and plain parts, cards) turns the link preview off, because a preview makes the Telegram servers fetch a URL that the model chose. `sendRichMessage` has no such option; the smoke script records whether it previews.
- **Stream errors.** A stream that is cut, ends before `message_stop`, or sends bad JSON throws the base error of the SDK. It is transient, so the slot runner retries it and records the call.
- **Polling and menu.** Polling names `allowed_updates: message, callback_query, stopped_message_generation`. `setMyCommands` is scoped to the owner's chat, is not awaited, and logs a failure.
- **Commands in code.** `/status`, `/goals`, `/approvals` and `/dashboard` answer from the router and the database before the queue, with no model call and no event. `/status` shows the reply in progress with its time and its running tool, the waiting messages, the last reply with its status and error, the pending approvals and the state of each integration. `/approvals` sends up to 10 live cards again. `/new` stays in the queue.
- **Card.** M1's per-field lines stay, with every security mark, instead of one summary line. Under them an expandable quote holds the exact redacted input as pretty JSON; this is the only message with `parse_mode: 'HTML'`. Long details keep 70% at the start and 30% at the end, with the count of the cut characters. On a 400 the card goes out as plain parts: the plain text holds the full details, so it is split like any plain text, and the buttons go on the last part.
- **Always allow.** Only for an `external` tool without `needsApproval`, and only on the first card: an allow rule for a `write` tool would also hold in a tainted session and skip the review. The confirmation names the scope (any input, every session, a tainted session still asks) and the gap: text that a tainted session saved as a goal or in memory can steer a later clean session, for example after `/new`, which then runs the tool without asking. Before M4 every external call of a clean session still asked, so this gap could not reach an external action; the fix is to carry taint through goals and memory (see the known gaps after M1). Its "yes" carries an expiry 10 minutes ahead, and an expired yes changes nothing. The rule is checked by `loadPolicy` in a temporary file, renamed into `okc.policy.json`, and only then does the approval resolve; a rule that the file already has is not added again. A rule written from `npm run chat` reaches the service at its next restart. When the file cannot be written or replaced (read-only, or locked by an editor on Windows), the temporary file is removed and the owner gets the reason; the approval stays pending.
- **Proactive text.** The heartbeat notification, `message_owner`, and the replies of automations (isolated and main session) go out as markdown through the same sanitizer. The decision named only the isolated relay; a main-session automation reply is model text too, so it was added.
- **Dashboard login.** `dashboard.publicUrl` takes an https address only, and its host is accepted only with `DASHBOARD_TOKEN`. `/dashboard` sends `<publicUrl>/login?code=<128 bits>`; a code works one time for 5 minutes and lives in the memory of the process that runs the dashboard. `GET /login` is a static page that does not spend the code; only `POST /api/login {code | token}` sets the cookie. Each sign-in gets a random 256-bit id that lives in the memory of the process, never a value derived from the token: a browser sends a cookie to every port and path of its host, so other local servers and other services shared on the tailnet name receive it. On the public host the id lasts 30 days (`HttpOnly; SameSite=Strict; Path=/; Max-Age=30d; Secure`) and is accepted only there; on loopback it lasts at most 12 hours, as a cookie without `Max-Age`. A restart or a new token signs out every browser. The codes go out only after this process's dashboard listens; if another process holds the port, `/dashboard` says so and names the port. Without the token or the address, `/dashboard` says what to set, and the commands link to the local address, because the dashboard answers the public name only with the token.
- **Follow-ups.** A "what the owner got" page with a deliveries table; the results of `scripts/smoke-telegram.mjs` (whether rich messages preview a bare URL, which would need a rule for bare URLs, and how Telegram shows a zero-width space in a tag name).

### 7.2 Decisions from phase 2 M4, verification round 3

- **Dashboard sessions in memory.** A public sign-in no longer survives a restart; the owner sends `/dashboard` again. Storing a hash of each id in the database would keep it over a restart, but it needs a new table for a rare event. A random id can still be replayed by another service on the tailnet name until it expires, so `docs/setup/tailscale.md` says to share nothing else on that name.
- **NO_REPLY in drafts.** A draft never shows a text that is a prefix of `NO_REPLY`, because no message replaces the draft of a reply that is not sent. The first empty draft still shows "Thinking…" until Telegram drops it, about 30 seconds after the last draft.
- **The reply in flight.** From the end of the run until its reply is out, `/stop` says that the reply is already going out and `/status` says "Sending the reply." instead of naming an approved call or an automation. `/new` matches in any case, as `/stop` does. `/status` takes the last run with the trigger `message` as the last reply, because a memory flush starts inside the run of a reply.
- **Always allow checks the tool again.** The confirmation and the yes button look up the tool in the current config. Only an `external` tool without `needsApproval` gets the rule, so a card from before a restart cannot add a rule for a tool that is now `write`.
- **A part with no plain text.** When Telegram refuses every format of a part and its plain text is empty, the send fails, so the router clears the reaction instead of showing the done mark.
- **Card keys are redacted.** The model writes the keys of a tool input too, so the card redacts a key and marks its field, as it does for a value.

### 7.3 Decisions from phase 2 M4, verification round 4

- **One more try after a 429.** This changes 7.1: a 429 tells that Telegram did not carry out the request, so the adapter waits for `retry_after` (at most 30 seconds) and sends the same message once more. A second 429 goes up as before. The drafts, the typing and the reactions of a reply make a 429 on the reply more likely. A reply that still fails is only logged; the session does not learn about it (open).
- **The split always ends.** A line that opens a code fence again in the next part is at most a quarter of the room. A longer line is replaced by its marker, and a longer marker is not carried. Before, a long one-line code span filled each later part, and the split ran until the heap ran out.
- **Redacted keys never merge.** A redacted key that is already taken gets a number (`"[redacted] 2"`), so the card details and the dashboard show every value that the tool gets.
- **Character references in the HTML fallback** show as their characters in text and in link addresses. Code keeps them as text. The converter knows the common named references; other names stay as text.

### 10.1 Decisions from phase 4 M3

The workshop reuses the approval flow of M1 as its only gate. There is no new table, no draft state and no dashboard page. The only migration adds `approvals.unsentAt`: the flow writes it when the card of an approval did not reach the owner. Code is in `src/skills/workshop.ts` (selection, review input, job) and `src/skills/skill-write.ts` (the tool, its checks, the write).

- **A daily review, not a review after each run.** A system automation `skills: daily review` (payload `{type: 'workshop'}`, slot `consolidation`, 09:00 in the owner's time zone) reviews the main session. The automation gives the claim, the missed-run rule, the backoff, "run now" and a pause by chat at no cost, at most one model call a day, and cards at a waking hour. The cost: a proposal comes the next morning. A review after each run with an idle wait was rejected: it needs tick logic beside the scheduler and has no daily limit.
- **Code picks the tasks.** A message run of `main` is long at 8 or more `tool_result` events. It is corrected when the next owner message matches `correctionIn` (a curly apostrophe from a phone keyboard counts as a straight one; a start word can follow a short lead-in such as "wait,", a quote or a dash; "wrong", "incorrect", "not what I" and a trailing "instead" match anywhere), the run used a tool, and no `/new` lies between them; both runs then form one task, and a chain of corrections joins into one task. Only a correction joins runs: two long runs next to each other stay two tasks, so a cut never hides a whole task, and a task over the limit is named in the "the last N are left out of this review" line. At most 5 tasks of 12,000 characters each go to the review. In a normal window the tasks over the limit are left out. Only in a window that a lost draft opened again, where the tasks that were reviewed already come first, does the review cover just the time up to the start of the first task it leaves out: that time is its mark and the end of its window, so the next review starts there. Carrying the overflow of every window was tried and rejected: with more than 5 tasks a day the reviews fall one more day behind each day, and the one-week floor then drops the same tasks a week late. A window without a task makes no model call: the job ends `skipped` with "no long or corrected task from … to …". `correctionIn` is English only: on a labeled sample of 30 synthetic messages it finds 16 of 18 corrections and matches 4 of 12 normal messages, and a test pins this. A false match costs input tokens of the daily call; a miss is silent. A classifier model was rejected: it is a model call on every owner message.
- **The window follows a mark.** The setting `workshop_reviewed_until` is the end of the last window that a review finished (an empty window, or a review run that ended `completed`). The next window runs from the mark to the start of today, at most 7 days back; without a mark it is yesterday. So a failed review or a day with the PC off at 09:00 (the scheduler skips a run more than 2 hours late) is reviewed the next time. A task across the window start can be reviewed twice; the second review sees the first skill in the index. A review that made a `skill_write` approval counts as finished for its window, also when it then failed or the app stopped: a retry would send a second draft for the same task. Its mark is the window end that it stored with the window start in the setting `workshop_window:<runId>` before it ran (removed after a review without a draft), so a later change of the time zone does not move it. A draft is lost when it expired before it ran and the owner approved it (the app stopped first) or never got its card (`unsentAt`, for example the network was down after the PC woke). A lost draft opens the window of its review again: the next window starts at the earlier of the usual start and that window start (still at most 7 days back), also when the review itself ended `completed` or no mark existed. The next review that finishes or makes a draft adds the ids of the lost drafts that it saw to `covered` in that setting, so each lost draft opens the window once. It adds only the drafts whose stored window end is not after its own end: when the task limit cuts the window, a lost draft whose window goes past the cut stays lost, and its stored window start moves to the cut, so the next review starts at the first task that was left out (a correction just after midnight can join a run of the old window to a new task, and without the move each review showed the same five old tasks until the 7-day floor). The record is for each draft and not for each review, because two drafts of one review get lost at different times: an approved draft 35 minutes after the approval, an unsent card after 24 hours. The owner's expiry message for an approved draft says that the next review looks again instead of "Ask again"; an unsent card expires silently, and the next review sends a new card. The review input lists every `skill_write` draft requested since the window start with its state (waits for the owner, approved, denied, not answered, or lost and why), and tells the model not to propose again a draft that the owner denied, let expire, or that waits for the owner, so an opened window does not repeat the decisions of its other drafts. The names in that list are model text of earlier reviews, so the review also carries the session taint of each review whose draft it lists. Each review with a draft gives its own mark. A mark after the window end (written while the clock was ahead) is ignored by itself, so the other marks still count; without a mark the window starts yesterday. The job runs one review at a time: a "run now" while a review runs ends `skipped` ("a skill review is running now"), because both would review the same window and send two drafts of one task. `npm run chat` passes the scheduler an `owns` filter that leaves the workshop automation out, so chat never claims the 09:00 review from the service (a claim moves `nextRunAt` to the next day), and the filtered job does not set the timer of chat; a "run now" in chat ends `skipped` ("left to the background service"). (Replaced by 10.3: `npm run chat` runs no scheduler.)
- **Only the background service reviews.** `AppDeps.background` (default true; `main.ts` passes `!chatMode`). In `npm run chat` the job ends `skipped` ("left to the background service") and does not move the mark, because its card would go to the terminal. (Replaced by 10.3: `AppDeps.background` now only keeps the scheduler of chat from starting.)
- **The review sees the procedure, not the data.** The review runs in `workshop:<runId>` with only `skill_read` and `skill_write`, the workshop instructions and USER.md. Its first event holds the tasks: each untrusted tool result and each tainted `system_event` becomes `[N characters of untrusted content from <source>, left out]`, a repeated line becomes one line with `(xN)`, and a long task keeps its start and end, cut between entries. Each line of an entry after its first is indented, so only code starts a line with `owner:` or `## Task`, and a tool result cannot pose as an owner correction. The taint of each task (from the last `/new` to the end of the task) still goes on that event, so the decision snapshot and the card name the sources, and the card adds the tool's `taintNote` warning. The event also lists each skill with `version` (the first 12 hex characters of the SHA-256 of its file). It is in the event and not in the stable prompt, so the prompt of other sessions does not change.
- **`skill_write` is the gate and the only writer of `skills/`.** It has `needsApproval: true`, so an `okc.policy.json` allow rule cannot skip the owner; the decision row, the card and buttons, `/approve N`, the compare-and-set resolve, the 24 h expiry, the at-most-once claim and the trace row all come from M1. Its input: `name` (for a new skill lower-case words with single hyphens, at most 64, not a Windows device name; for a change the exact name of a skill that exists, so a skill that the owner named by hand, such as `weekly_review`, can be changed), `description` (one line, at most 200), `body` (at most 2,500 characters and 80 lines), `replaces`, `base` (required when `replaces`), `why` (at most 300). Every control, format and default-ignorable character (`\p{Cc}`, `\p{Cf}`, `\p{Default_Ignorable_Code_Point}`) and the line separators are refused in the description, the body and `why`, except one variation selector after an emoji and a joiner between two emoji parts. A run of 4 or more combining marks is refused too: a reader draws a long stack over the lines next to it, and real text puts at most 3 on one letter. This set holds every character that the card shows as a `\u` code, and a test walks all of them, so a draft that passes has no hidden text (for example tag characters, which can spell an instruction) and keeps the card size. A description that the loader would read in another form (only spaces, or in matching quotes) is refused, because the loader would leave the skill out. A registered secret is refused too: the card would show `[redacted]` while the file got the real value. The schema runs again when the approved call runs.
- **The card shows the whole body.** `Tool.fullFields` (`description` and `body` for `skill_write`; the description goes into the skills list of every prompt) names input fields that `describeInput` shows in full and never cuts: redacted, invisible characters as `\u` codes, other line breaks escaped, each line behind `│ `, so a body line cannot pose as a card line. The other fields stay one-line JSON. A run of text that mixes Latin with another script gets one mark per full field, with the count of runs and up to 5 code points; a quote of each run would repeat the text that the field shows. The worst card without a taint line is 4,034 characters (80 lines, a 2,500-character body, a 200-character description, a why made of quotes, and runs of Latin and Gothic letters in each field), so it fits one Telegram message; without mixed scripts it is 3,505. A long taint line can still make the adapter split it, with the buttons last. The Telegram adapter sends every message with link previews off: Telegram fetches the first link of a message for its preview, so a link in a draft could send data to an outside server before the owner presses a button. M4 telegram must keep this contract (one message, previews off) when it rebuilds the card. At the merge, the M4 card added the exact input as details: in an expandable quote when at least 300 characters are left, else in plain parts after the text. A skill card near the limit then split, so a card text with no room for the details now goes out alone when it fits one message.
- **The write checks the folder when it runs**, because the owner can change it while the draft waits:
  - a file that already has the new text gives "already saved", so a write that runs again after a crash is harmless;
  - a change whose file has another version than `base` writes nothing ("the skill changed after the draft … the file keeps the newer text"), and a change of a deleted skill makes nothing;
  - a new skill is refused when a skill or a folder of that name exists, in any case. A folder that holds only temporary files of a stopped write holds no skill, so the write removes them and uses it; a failed write of a new skill removes the folder that it made. Otherwise one failed rename blocks the name until the owner deletes the folder by hand;
  - code renders the frontmatter, and a change keeps every frontmatter line other than `name` and `description`;
  - the real path must be inside the real skills folder; the write goes to a temporary file and a rename, and a failed write removes the temporary file. The loader already ignores junction folders, so through the tool only a swap between the check and the write reaches this check.
  - the result of a change holds the old text, so the trace keeps every version.
- **`/skills/` is gitignored** (anchored at the root, so `src/skills/` stays tracked). Skills come from the owner's tasks and can hold personal details, the same reason as `workspace/USER.md`. Remove the line from `.gitignore` to track them in git.
- **Rejected:** a draft table with its own buttons (a second approval path beside the hardened one), a diff on the card (the card shows the exact text that gets written, and `why` says what changes), a `Tool.describe` hook and a Workshop page, a config block and a new model slot.
- **Known gaps.** Approval turns text from a tainted task into a lasting instruction; the defences are the input without untrusted content, the warning, the source line, and the owner reading every line. The cap of 2 proposals per review is a prompt rule; the iteration limit bounds it in code. A model that copies `base` wrong makes Approve write nothing, with an honest message. The check-then-rename window (milliseconds) can lose a hand edit. An approved write that a crash interrupted is asked again through the generic "effect unknown" path. A draft that the owner denied and that was requested before the window start is not shown to later reviews.

### 10.2 Decisions from the phase 1 audit: crash safety

- **A graceful stop does not call `process.exit`.** It sets `process.exitCode` and lets the event loop drain, with an unref'ed 5 s timer as the fallback. The audit saw `UV_HANDLE_CLOSING` assertions (exit `0xC0000409`) when `process.exit` ran right after network calls on Node 24.11.1. A local probe (two keep-alive `fetch` calls to http and https fixture servers, by name and by address, 0 to 30 ms before the exit) did not reproduce it, so the fix rests on the audit's runs; the change is safe either way.
- **`okc stop` asks first.** Windows has no signal that a script can send to the hidden agent, and `Stop-Process -Force` skips the end of the runs. The agent writes a random token to `data/okc.stop-token` at each start; `POST /api/shutdown` with that token (json, so a browser page cannot send it without CORS) runs the same stop as SIGINT. `okc stop` gives the agent 10 s, then forces the stop. The dashboard token does not stop the app. Rejected: a stop file that the app polls (slower, one more timer), and sending Ctrl+C through `GenerateConsoleCtrlEvent` (needs a shared console).
- **A one-shot job of a stopped process runs again or is recorded as missed.** The claim of an `at` job sets `nextRunAt` to null, so a stop during the run left the job enabled with no time. Each tick gives such a job its planned time back when the claim is older than the age limit of stale runs and this process does not run it; the missed-run rule then decides. Rejected: a `running` row in `automation_runs` at claim time (a second write path for the same fact).
- **Crash evidence stays.** Each supervised start writes its own `service-<time>.out.log` and `.err.log` (the last 10 starts stay), `service.restarts.log` has the exit code in hex (`$node.Handle` is read, or the code stays empty with redirected output), uncaught errors and rejections go to the log file with secrets redacted and exit with 1, the console shows only warnings, and `okc-*.log` files older than 30 days are deleted at start.

### 10.3 Decisions from the phase 1 audit: single instance

- **One service for each data folder.** Before it opens the database, a process that is not `npm run chat` listens on a named pipe whose name is a hash of the real path of the data folder (lower case on Windows). A second service gets `EADDRINUSE` and ends with exit code 1 and a clear message. Windows removes the pipe when its process ends, also after a crash or `Stop-Process -Force`, so the lock never stays behind and a reused pid cannot hold it. Rejected: a `data/okc.lock` file opened with `wx` and a pid in it (a crash leaves the file, and a stale check by pid is wrong when Windows gives the pid to a new process, so the service could refuse to start for ever), a lease row in SQLite (a crash holds it until the lease ends, and it needs a renew timer), and a fatal `EADDRINUSE` of the dashboard (the port can also belong to another program, and the agent must work without its dashboard). On Linux the name is in the abstract socket namespace, which the kernel also removes; that branch is not checked on a Linux machine yet. macOS has no abstract socket namespace (`listen` gives `EINVAL`), so on darwin the lock is a unix socket file `okc-<hash>.sock` in `os.tmpdir()`. A socket path must fit the 104-byte `sun_path` field with its end byte; when the path in the temp folder is longer, the file goes in `/tmp`. The file stays after a crash, so on `EADDRINUSE` a `connect()` probe decides: a process that answers holds the lock, and the start stops; `ECONNREFUSED` (or `ENOENT`) means a stale file of a process that ended, which is unlinked before the listen is tried once more. Any other error, for example from a file that is not a socket, is not removed, and the start stops with the error. Two starts that find the same stale file at the same moment can both get past the probe; launchd and `okc.sh` start one process at a time, so this does not occur in normal use. A clean stop removes the file through `server.close()`. Linux keeps the abstract socket and win32 the named pipe.
- **`npm run chat` runs no scheduler.** It is a client of the same database. It took main-session reminders and check-ins and sent them to its own terminal; the compare-and-set claim stopped double runs, but not this. The `owns` filter of the scheduler (10.1: chat left the skill review and the polls to the service) and the review's own "left to the background service" check are removed, because chat no longer ticks. A reminder that is due while only chat runs waits for the service. Rejected: a wider `owns` filter (chat would still tick each minute and run the sweep and the one-shot revival for nothing).
- **Polling that ends stops the process.** grammY ends polling on a 401 or a 409 and tries other errors again. The adapter calls `onPollingFailed`, and `main` stops the app with exit code 1, so the supervisor logs `exit=0x00000001` and starts it again after its growing wait (at most one minute). A wrong token therefore restarts once a minute; that is cheap and shows in `okc status`. On darwin launchd restarts it, because `KeepAlive` has `SuccessfulExit` false, and the plist sets `ThrottleInterval` to 60, so the wait there is a fixed minute. `okc status` shows the `runs` and the `last exit code` that launchd keeps. No channel state goes to `/status` or the Overview page: `/status` cannot reach the owner while Telegram is deaf, and the process that failed ends within seconds. Rejected: a restart of polling inside the process (more code for the same effect, and a 401 does not heal by itself).
- **A button press is not lost when its answer fails.** This was already true (7.1): the adapter does not wait for `answerCallbackQuery`, logs a failure, and passes the press on; a test pins it.
- **The okc scripts trust a pid only for the right process.** `okc.ps1` reads a pid file only when it holds a number and the command line of that process runs the `run.ps1` of this folder (the agent: `dist/main.js` with the supervisor as parent). Any other file is deleted. `run.ps1` holds the mutex `Local\OkComputerSupervisor:<folder>` for its life, so a second supervisor of the same folder ends at once; an abandoned mutex after a forced stop counts as taken by the next supervisor. A test runs the real scripts against a temporary folder with a fake agent. `okc.sh` on macOS and Linux follows the same rule: a pid from a pid file counts only when `ps` shows that its command line runs `$root/dist/main.js` of this folder. When launchd manages the agent, the script uses the pid that `launchctl` reports for `com.okcomputer.agent` and not a pid file.

### 10.4 Decisions from the phase 1 audit: theme scheduler

- **Only a one-shot job is turned off after five failures.** The retries take about 21 minutes, so a short outage of the model or the network turned off the heartbeat, the polls, the consolidation and the day results for good; the heartbeat came back only when its interval changed. A recurring job (`cron` or `every`, from any creator) now keeps its failure count and runs again at its next normal time, and the owner gets one message for each series of failures ("I keep it on", with the next time). After the fifth failure, each normal run has one try until a success resets the count; a new ladder of retries for each normal run was rejected, because a broken heartbeat would then cost five model calls in each interval. Rejected: the rule for system jobs only (an owner's hourly job has the same problem, and a failed job costs no more than a successful one).
- **The consolidation and the day results catch up for one day.** Their grace period is `max(scheduler.missedGraceMs, 24 h)`, and each run gets its newest planned time at or before now (`previousRun`, croner's `previousRuns`) as `nextRunAt`. A morning after a night of sleep runs both jobs for the right day, a retry of the 23:45 results after midnight still writes the planned day, and after a stop of more than one day the newest missed day runs (older days are not replayed; their daily notes stay). Rejected: a claim that plans from the start of the grace period (it gave a `nextRunAt` in the past, so a later due run could start while the first still ran), and the planned time only for retries (the catch-up needs it too).
- **The day results replace their own lines.** The setting `goals_results_written` keeps the day and the lines of the last run; a second run for that day (a retry, a run now) replaces the last copy of those lines in each section and leaves the lines of the owner and the agent. Only the last day is kept, because a rerun of an older day needs a run now on purpose. Rejected: a pattern that finds the results lines (a `- title` line of the agent looks the same).
- **A one-shot job that moves itself stays on.** The end of a successful run turns a one-shot job off only while its `nextRunAt` is still null.
- **A cron has five fields.** croner reads a sixth field as seconds and a seventh as years, so `*/5 * * * * *` got past the one-minute minimum. The nicknames such as `@daily` are refused too; five fields say the same.

### 12.2 M0: macOS and Linux bring-up

- **Instance lock.** On darwin the lock of `src/instance.ts` is a unix socket file in `os.tmpdir()` (`okc-<hash>.sock`), or in `/tmp` when that path is too long for the 104-byte `sun_path` limit. A crash leaves the file behind, so a start that finds it tries to connect. When no process answers, the start removes the file and takes the lock. A file that is not a socket is never removed. The name of a data folder that does not exist yet comes from the real path of the nearest folder above it, so a link such as `/tmp` gives one name. Windows keeps the named pipe and Linux the abstract socket (10.3).
- **Node 26.** The emoji parts of the `skill_write` check are an alternation, so Node 24 and 26 both accept a joined emoji (D1).
- **The decompression-bomb test** builds its body from 50 gzip members of 1 MB, so the 40 MB limit measures only the reader on macOS too. The limit of the reader did not change.
- **Chrome** is found at the darwin and linux paths, and only at absolute paths. On POSIX the profile lock reads the `SingletonLock` link and checks the pid with `kill(pid, 0)`. A pid that is too large counts as a busy lock. `openssl` is found on `PATH`.
- **Stdio MCP servers** run detached in their own process group on POSIX, and a stop kills the whole group.
- **`scripts/okc.sh`** and the LaunchAgent are described in DESIGN.md §18 (D3). The service sets `OKC_SERVICE=1`, so the agent runs no cli when it runs as a service. The script finds its folder through any link.
- **The credential store** has platform-neutral words in the texts that the owner sees. On macOS it is the login Keychain, and the setup docs use `security` where Windows uses `cmdkey`. When the agent first reads an entry that `security` made, macOS asks whether `node` may read it. The owner chooses **Always Allow**, and macOS asks again after each node update ([setup/integrations.md](setup/integrations.md)).

### 12.3 M1: chats, search and spans

The endpoints, their errors and their paging are in PHASE5-API.md (M1). The design of the chat list, the search index and the stream is in DESIGN.md §16.2 ("Chats and search", "Stream").

- **Chat keys.** Each segment of `main` between two `session_reset` events is one chat, with the key `main@<id of its reset>` (`main@0` before the first reset). A background session is one chat. The key rules live in `src/dashboard/chat-keys.ts`, which chats, search and the stream share. The sort and the cursor of `/api/chats` are in SQL, and the numbers of a chat are read only for the chats of the page. With `q`, a page reads at most 500 background chats.
- **Delivered text only.** A chat shows the owner messages, the guarded final reply of each run (its last `assistant_message` with no tool calls, or a turn whose call made an approval), the notes and the system events that the chat shows. The text of other tool turns was a draft, and the chat never got it. Search uses the same rule, so a `NO_REPLY` answer, a draft and a held reply give no hit.
- **Search index.** `018_search.sql` makes `events_fts` (FTS5, trigram) with an insert trigger and a backfill, and the indexes `events_run` and `runs_started`. A payload that is not valid JSON gives no text, so the insert never fails and the event log stays append-only. A query of 3 or more characters is one quoted phrase, and a shorter one scans with `LIKE` (D6). NUL characters are dropped before the checks.
- **Spans.** `/api/runs/:id/spans` computes the start and end of each span on the server. Child runs nest under their sub-agent span. A `sandbox` span is read from the rows of `020_sandbox.sql` only when the table has the columns that the spans use.
- **Stream kinds.** `/api/stream` adds `model_call`, `tool_call`, `browser_step`, `approval` and `policy`, with ids and summaries only. A pending approval and a review or approve decision of a running run are read again on each poll, so a later verdict or approval goes out too.
- **Paging and limits.** `/api/runs` gains `sessionKey` and `before`, and `/api/logs` gains `day` and `runId`. A `day` that is not a date of the calendar gives `400`. The limit and id rules are in `src/dashboard/params.ts`.

### 12.4 M2: web chat

The design is in DESIGN.md §10 (**web**), and the endpoints are in PHASE5-API.md (M2).

- The web channel starts only when `DASHBOARD_TOKEN` is set, because it runs the main session as the owner with all its tools. Without the token every chat route answers `503`.
- **Limits.** A message is 1 to 16,000 characters, and a text of only spaces gives `400`. Button `data` is at most 256 characters, and a `turnId` at most 200. The bodies are strict, so an unknown key gives `400`.
- **Turns.** A `turnId` is the `messageId` of the inbound message (`web:<uuid>`, or `telegram:<message id>`). The router calls the turn hooks for every channel, so a run that Telegram started streams to the open web clients too. A stop of a turn that still waits in the queue gives `stopped: false`.
- **Buttons** carry a mark from a key of each process, as Telegram buttons do. A press without a valid mark does nothing, so a button that the model wrote into a reply cannot resolve an approval. The marks are new after a restart.
- **Proactive messages** never go to the web channel and never make it the saved `owner_chat`. A copy goes to the chat stream as a `reply` with `turnId: null`, so an open tab shows the approval card.
- **Model text** is rendered as markdown with no raw HTML. No image loads without a click, and only `http(s)` links are clickable.

### 12.8 M8: inbox jobs

The endpoints, their `409` answers and the tools are in PHASE5-API.md (M8). The owner's guide is [setup/google.md](setup/google.md), section 4.

- **The jobs are code.** Each job runs in the session `inbox:<job>:<runId>`, and each dashboard action in `inbox:action:<runId>`. The first event of each run is a `system_event` with its task, so the reviewer reads what the run may do. One run of a job goes at a time.
- **Automations.** The payload is `{ type: 'inbox', job }`. The app installs three system automations one time: `inbox: daily digest` at 07:30 every day, `inbox: newsletter sweep` at 09:00 on Saturday and `inbox: subscription finder` at 10:00 on Sunday, in the time zone of the app. The owner changes them or turns them off on the Automations page, and the app never puts a deleted one back. A job that could read no account fails, so the scheduler backs off.
- **The digest** reads the last two days of the inbox of each account, sorts the mail with a model on the utility slot into needs a reply, deadlines, bills and packages, stores the digest for the Inbox page and sends a short text to the owner. It asks for a draft for each mail that needs a reply, and for a calendar proposal for each course or bill deadline.
- **Drafts** go to Gmail Drafts through `inbox_draft_reply`, which the reviewer checks. The app never sends a draft or a mail.
- **Calendar proposals** are approvals of `inbox_create_event`, so the event is made only after the owner approves it. The event id comes from the proposal and a salt of the install, so a second run of an approved call finds the first event and makes no copy.
- **The newsletter sweep** groups senders by `List-Id` or `From`, with read rates. An unsubscribe uses one-click (RFC 8058) or the https link, needs a DKIM signature of the From domain that covers `List-Unsubscribe`, and takes the link from the newest signed message. A `mailto` unsubscribe is only shown. An archive asks the owner and never adds a Gmail system label.
- **The subscription finder** finds receipts and recurring charges and builds the table (merchant, amount, cadence, last charge, source mail, confidence). The monthly totals leave out cancelled and ignored rows. A later charge makes a cancelled subscription active again.
- **Browser help.** An approved https unsubscribe or cancellation starts a browser run in `auto:inbox:<runId>` on the `main` slot, with the facts from mail in an untrusted block. Each form send asks the owner. The row stays pending while the run works, and goes back to `active` with an error when the run fails or the owner denies a step.
- The tables are in `019_inbox.sql`. Without a `google` block the lists are empty and the `POST` routes give `503`.
